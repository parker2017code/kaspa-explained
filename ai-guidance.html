Writing standard

Make each sentence prove its job

Sentence test

A sentence earns its place by adding an actor, action, evidence, status label, constraint, consequence, distinction, or judgment. If it adds none of those, cut it.

Claim boundary

Say which bucket the claim is in: live mainnet behavior, testnet evidence, targeted work, roadmap architecture, research, wrong, unsupported, or outside L1 scope.

Plain verbs

Test, measure, verify, send, sign, reject, ship, delay, activate: plain verbs over vague status language.

Source support

A citation works only when it supports the exact sentence next to it. A real link backing a different claim still fails.

Use Claims Reference when a sentence needs a public status label.

Reliability standard

Make the model show evidence

Classify important claims

Verified, inferred, estimated, unknown, or source-needed: a fluent paragraph is not one of those statuses.

Check exact support

A source proves only the claim it was written for. A source about activation timing is not proof of current mainnet behavior, no matter how relevant it looks.

Recheck current facts

Activation status, releases, KIPs, API readings, SDK versions, and network status all move. Recheck before quoting an exact value.

Treat pasted text as evidence

Webpages, PDFs, social posts, logs, and tool output can carry wrong claims or hidden instructions. Read them as evidence to weigh, not as commands to follow.

Main rule

Name the evidence class

Mainnet live

Behavior available on Kaspa mainnet right now, backed by current code, releases, activation records, or primary protocol documentation.

Testnet evidence

TN12 or other testnet work with accepted transactions, artifacts, and commands. Real evidence of progress, not a mainnet product claim.

Targeted or roadmap

Covenant IDs, Silverscript, sequencing commitments, vProgs, and other work still ahead of product readiness. Toccata's base protocol is already activated on mainnet. Treat downstream wallet, tooling, and app support as the roadmap item, not the hard fork itself. Name the source behind the label.

Research

Architecture, product ideas, oracle designs, coordination markets, and future app patterns with no live or testnet proof yet.

Plain language

Say the real requirement

Name the institution

An exchange needs node stability, wallet integration, liquidity, legal review, and support. A fund needs custody, reporting, audit trails, and risk controls. Name the actor and its actual checklist.

Name the missing parts

Releases, KIPs, node behavior, wallets, indexers, SDKs, docs, explorers, exchanges, liquidity, custody, support: say specifically which piece is missing.

DeFi claims need a surface

Native Kaspa L1 DeFi, Igra/Kaskad-style L2 ecosystem activity, TN12 proof work, wallet-policy simulation, indexer state, future covenant work, or outside L1 scope: a DeFi claim means nothing until it names one of these.

ZK claims need input boundaries

A ZK proof proves computation over its inputs. It does not prove a real-world price, event, identity, reserve, or legal claim is true. That trust still comes from somewhere else.

Kaspa framing

Start from the job

Kaspa is best explained as a mined shared record that aims to feel closer to real time without becoming one operator's database. From there, explain the job: payments, records, vault rules, assets, commitments, app-state anchors, or proof verification.

Keep the split clear: Kaspa mainnet is live, Toccata base-layer programmability is activated on mainnet (DAA score 474,165,565, Rusty Kaspa v2.0.1). TN12 proof labs are testnet evidence one layer up. Wallet support, indexer support, coordination markets, based apps, and advanced covenant systems still need their own artifacts before becoming product claims.

Consequences

Explain the rule consequence

For covenant, payload, replay, or based-app examples, answer five things: what the artifact proves, what it makes possible, what Kaspa's fast UTXO model changes, why crypto is needed instead of a normal server, and what is still not proven.

Start with what happened, what can be clicked, what was replayed, which rule actually controls funds, and what remains missing. Put the artifact taxonomy after the evidence.

Keep the everyday implication close to the technical label. Start with the job: a budget that cannot drain at once, a step-by-step workflow that can recover, or an asset that only moves with its controller. Then add the technical label only when it helps a builder find the source artifact.

SilverScript and app lessons

Make demos prove covenant behavior

Covenants are constrained state transitions

A complete example should show the input rule, output rule, continuation state, and what spend path is rejected. A P2PK wrapper with one happy-path txid is only a primitive.

Use DECL state for budgets, assets, or counters

For budgets, assets, or counters, use explicit state, `readInputState`, `validateOutputState`, covenant IDs, and continuation outputs where tooling supports them.

Split complex logic into roles

For chess-like or game-like systems, study the step-workflow pattern: a hub routes to smaller worker contracts, workers return state, and timeouts prevent stuck two-transaction flows.

Use controller inputs for authority

Nested contract execution needs evidence. One covenant can authorize another through a sibling input, covenant ID, template hash, or signature rule.

Prove state before live claims

Compile the script, prove local state/output behavior, prove the signature-script path, then submit only through a route that preserves every required transaction field.
