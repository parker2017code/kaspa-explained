What is Kaspa?

Kaspa is a live proof-of-work blockDAGBlocks arrive in parallel and all of them are kept, so the record is a graph rather than a single line. network. Its native coin is KAS. The network keeps Bitcoin-style mining and UTXOUnspent transaction output. Value sits in separate coins, spent whole and replaced by new ones, instead of living in one account balance that gets edited. ownership, and GHOSTDAG orders parallel blocks into one payment history.

Limits get their own page: Risks and Open Questions covers adoption, node load, and security budget.

The core move

Parallel blocks are the whole design

A block takes time to reach the rest of the world. When blocks outrun that propagation, miners build on stale information and produce competing blocks a single chain can only keep one of. Bitcoin's answer is to make blocks rare, roughly one every ten minutes, so collisions stay rare too.

Why rare blocks are the fix, and what it costs

At a ten-minute interval, propagation delay is small next to the interval itself. Most blocks finish spreading before the next one is found, so a collision is a rare accident rather than routine, and Bitcoin never needed a rule for keeping both sides of one: discarding the loser is cheap enough.

The cost lands on confirmation time instead. A payment needs several block intervals to be safe, which is why it settles at the pace it does rather than in seconds.

How this works, and the sources

Blocks arrive at random, a Poisson process with rate λ. A block collides with the one before it when the next block is found before the first has finished spreading, which takes time d. The chance of at least one collision is:

p = 1 − e−λd   (λ = block rate, d = propagation delay)

That is not the share this demo reports. A single chain that has already kept a block rejects anything mined before that block finished spreading, so a run of collisions keeps only the first, the way a non-paralyzable dead-time counter drops events inside its recovery window. Working that through gives a lower share:

discarded share = λd ÷ (1 + λd)    kept share = 1 ÷ (1 + λd)

Inferred from the identity above, matching this simulator's own discard rule rather than quoted from a source. At the opening settings λd = 2.51, so p works out to about 92% while the discarded share is about 72%. The running tally converges toward that second figure.

A single chain can only keep one block per collision, so the loser's work is wasted. A blockDAG references every block a miner could see when it started working, so both survive and get ordered instead.

Where this comes from. Poisson block creation at rate λ, with propagation delay as the cause of concurrent blocks, is the model in Sompolinsky, Wyborski and Zohar's PHANTOM/GHOSTDAG paper (eprint.iacr.org/2018/104): "Block creation follows a Poisson process with parameter λ," bounded by a network delay diameter D. Verified against that primary source.

p = 1 − e−λd is the simpler building block underneath the paper's own anticone bound: standard Poisson math, P(0 arrivals in time d) = e−λd, and the same collision mechanism the Bitcoin fork-rate literature uses (Decker & Wattenhofer, Information Propagation in the Bitcoin Network, IEEE P2P 2013).

Inferred from that identity, not quoted from either paper. This demo also tests only the immediately preceding block, not the full anticone GHOSTDAG resolves.

Below one block a second the display runs faster than real time, by the factor named under the slider. From one block a second up it is real time. The collision math always uses the real rate and delay, never the playback speed.

Kaspa keeps the fast blocks and fixes the order instead. A block points at every tip its miner could see, so two blocks found a moment apart both land in the record as parents of whatever gets mined next.

The word blockDAG names that shape. GHOSTDAG reads the resulting graph and derives the order. Kaspa's origin story covers how that research reached mainnet.

What you feel above is inclusion speed: mainnet makes ten blocks a second, so a broadcast transaction usually lands in a block within about a second. Inclusion is not settlement; the gap between them is what confirmations measure. Supply itself is capped on a fixed emission schedule with no premine.

    How the colors get decided

    Every block names the tips its miner could see when it was made, and those references are the whole data structure. A block's past is everything behind it, its future is everything built on top of it, and its anticone is everyone else: blocks that neither saw it nor were seen by it.

    Each block picks the parent with the most accumulated work as its selected parent, chaining block to block into a main chain. A block counts (blue) if the number of already-counted blocks in its anticone stays under the cap, k. Over the cap, it is locked out (red) instead.

    The DAG has no single "now": blocks keep arriving in parallel, with no one moment everyone agrees on. Kaspa's answer is the virtual block, a conceptual block that is never mined and never sent to anyone.

    It exists only on each node's own machine, standing in for everything that node has seen, and its parents, the virtual parents, are that node's current tips.

    Among those tips, the one with the most already-counted blocks behind it becomes the virtual selected parent, better known as the sink. That is the same rule an ordinary block uses to pick its own selected parent, applied one level up: to the node's whole view rather than to a single mined block.

    A block's anticoneBlocks that sit in neither a block's past nor its future. Nodes need an anticone rule to order these consistently. is everything neither behind it nor built on it. A single chain has no way to rank an anticone, so it discards one side. GHOSTDAG ranks it instead, by one behavioral tell: an honest miner publishes a block the instant it is found, and a miner building a secret history does the opposite.

    Why honest and hidden miners produce different anticones

    Within a propagation delay, everyone else sees an honest miner's block and starts referencing it, so its anticone stays small by construction. Nobody can reference blocks they were never shown, so a hidden miner's withheld blocks surface later carrying wide anticones.

    An attacker's red blocks buy no weight in the accepted history, so the electricity behind them is wasted. Honest parallel blocks are kept instead of discarded, so running the block rate up does not burn the security budget on orphans the way it would on a single chain.

    Confirmations

    Fast is not final

    1Seen

    Your wallet broadcasts the transaction and nodes pick it up.

    2Included

    A miner mines it into a proof-of-work block.

    3Ordered

    GHOSTDAG places it against the blocks mined in parallel.

    4Accepted

    Nodes accept it under Kaspa's consensus rules.

    5Confidence

    Reversal risk keeps falling as more blocks stack proof-of-work on top of it.

    Kaspa has no single stack to count. Your block sits in a graph, and what piles up on it is blue work: the proof-of-work carried by every later blue block whose history includes yours.

    Reversal risk falls as that weight builds, which is why Kaspa publishes no universal confirmation count. How long before a payment is safe to trust prices the wait against an attacker of any size.

    What actually sets a safe wait, and how finality depth differs

    Undoing a payment means producing a competing set of blocks heavy enough to outweigh the one the network already accepted, and every new block referencing your transaction raises that bill. Wallets and explorers report the result as a confirmation count.

    At ten blocks a secondWritten 10 BPS in Kaspa's own documentation. Kaspa ran at one block a second until the Crescendo activation, DAA score 110,165,000, and has run at ten since. those references arrive quickly, so the risk curve drops steeply in the first seconds. Steeply is not vertically.

    Three things set the honest wait: the value at stake, hash rate now and how much it swings, and whether the payment can be undone outside the protocol. A shipping hold takes a thinner wait than handing over a good nobody can claw back.

    Exchanges and payment firms publish their own deposit rules, and those are the numbers a user meets.

    Finality depthThe threshold past which old history counts as settled. is a different, deeper question: how far back the protocol will let anyone rewrite. It sits far past any payment wait, and once history is buried past it nodes reject a reorganization outright, which is also what makes pruning safe.

    Does pruning make Kaspa private?

    No. Pruning and missing explorer history are not privacy guarantees. UTXO state remains the consensus object, and a broadcast transaction can still be observed or archived by others before a node prunes it.

    Throughput

    Ask "TPS of what?"

    TPS is not one number. Kaspa mainnet makes ten blocks a second, and what fits in those blocks depends on what each transaction asks the network to do. A plain payment is cheap. A covenant or a proof is not.

    Transaction size

    size = 94 (fixed header: version, in/out counts, locktime, subnetwork id, gas, payload hash, payload length) + payload_bytes + inputs × (118 fixed bytes: outpoint 36, sig-script length field 8, signature script ~66, sequence 8; +2 if covenant/v1) + outputs × (52 fixed bytes (value 8, version 2, script-length field 8, P2PK-style script 34) + 34 per output, if that output carries a covenant id)

    C = STORAGE_MASS_PARAMETER (1,000,000,000,000) utxo_plurality(output) = ceil((63 + script_bytes + 32 if covenant else 0) / 100) A P2PK-style output (script 34) has plurality 1. A covenant-carrying output (63 + 34 + 32 = 129 bytes) crosses the 100-byte unit and has plurality 2, which squares its weight below. storage_mass = max(0, outputs × plurality² × C / out_amount_sompi − inputs × C / in_amount_sompi) in_amount_sompi assumes no fee: total out value split evenly across inputs.

    Which dimension binds

    Compute and storage share a 500,000 block-mass limit; transient's limit is 1,000,000, so it is normalized to the same scale before comparison: transient_norm = transient_mass × 500,000/1,000,000. tx_mass = max(compute_mass, storage_mass, transient_norm) tx_per_block = floor(500,000 / tx_mass) TPS = tx_per_block × 10 blocks/second

    This models a standard Schnorr P2PK-style input/output shape and assumes value is conserved with no fee. Real network TPS is lower once relay policy, fee markets, and mempool behavior are added on top of this pure mass ceiling.

    Where the payment numbers come from

    Kaspa mainnet makes ten blocks a second. Current mainnet params cap compute and storage block mass at 500,000, which gives a budget of 5,000,000 transaction mass per second before policy, fees, relay, storage shape, and real mempool behavior come in.

    A signed plain P2PK-style 1-input, 1-output payment costs roughly 1.6k mass by the code's careful math; add a change output and a 1-input, 2-output payment runs closer to 2.0k mass.

    Divide the block budget by those shapes and the count lands around 250 to 300 simple transactions per block, about 2,450 to 3,070 per second at ten blocks a second. Leaner shapes and rounding push the top end to the often-quoted 3.4k TPS.

    Benchmarks built on fake minimum-size transactions score higher than that, and what they measure is a lab ceiling.

    Anything that makes a transaction bigger, from extra outputs to covenant metadata to proof bytes, crowds out the simple transfers competing for the same budget. Kaspa's docs put the payload ceiling around 25 KB when payload data dominates a standard transaction, because the standard transaction mass ceiling and transient byte accounting still apply on top of it.

    Toccata leaves the payment limit alone. Transient mass rises from 500,000 to 1,000,000 at activation while the compute and storage reference limit holds at 500,000, and the Toccata guide ties that rise to fitting STARK-sized proofs.

    Toccata also adds v1 transaction fields such as output covenant data and input compute commitments, and raises the standard minimum relay fee. It is mostly an upgrade to what L1 transactions can say and check.

    Covenants

    A coin that can carry its own rule

    Since Toccata went live at DAA score 474,165,565, a Kaspa coin can carry a rule about how it may move next. The network checks that rule the same way it checks a signature: a vault can ask for a delay and a backup key, an escrow a release or a refund.

    What Toccata turned on, KIP by KIP
    KIP-17

    A UTXO can read the transaction spending it and require a matching next output: vaults, escrow, spend caps, refunds.

    KIP-20

    Covenant IDs give covenant state a lineage consensus tracks, blocking fake lookalikes.

    KIP-16

    A script checks a proof from a chosen proof system, initially Groth16 and RISC0-Succinct, instead of L1 running every app step itself.

    KIP-21

    Sequencing commitments let an app prove its own lane instead of almost the whole DAG.

    vProgs

    Not part of what activated. Full vProgs, for shared app state many users mutate at once, are still roadmap architecture. See status.

    Based apps

    Apps anchor state to Kaspa ordering and settle proofs back to it, with no separate sequencer.

    No virtual machine, no accounts, no global shared state. App logic lives in bounded UTXO steps or proofs. A live demo that tries to break a covenant vault is on build on Kaspa.

    What this page shows, what it can't, and why

    What the count is

    The tip count at the top is tipHashes from a live read of api.kaspa.org/info/blockdag: how many block tips the network is holding open right now. Each new tip is then fetched from api.kaspa.org/blocks/{blockId}.

    A sample, not the whole feed

    The API sits behind an 8-second edge cache, so this page checks every 9 seconds. Kaspa makes roughly ten blocks a second in that gap, so each check catches a handful of them, not all. The line above the feed states both numbers.

    Miner names are self-reported

    The payout address and miner tag come from the block's own coinbase data (extra.minerAddress and extra.minerInfo). Neither is a verified identity: a pool can rotate addresses, and the tag is a plain string the miner chose to write.

    Red blocks are real blocks

    A block tagged red was mined honestly but arrived too late in its local ordering to count in the accepted history. Keeping the block and deciding whether it counts is GHOSTDAG's job.

    Empty blocks are real usage

    A block carrying only its own coinbase transaction is marked Empty, and most arrive that way. That is Kaspa's current usage, not a failed read.

    Tags are read, never inferred

    A covenant tag means the API returned a network-verified covenantId; build-on-kaspa counts how many are running. An app: ciph_msg pill means the payload literally starts with that string.

    Anything else stays unlabeled rather than guessed. A ZK opcode call is not shown at all, because the REST API returns transaction scripts as opaque hex rather than decoded opcodes.

    What an explorer has that this does not

    Miner leaderboards, address balances and historical charts need a database of stored history. This page has one API read per visit, so it shows what that read contains.
