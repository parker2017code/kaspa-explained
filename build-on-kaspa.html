Route

Pick the route

Plenty of Kaspa products need only payments, receipts, or better wallet UX. Toccata matters only when the product needs a spend rule the user can read before funds move. Still deciding if Kaspa belongs at all? Check which jobs gain from Kaspa.

Two questions before the table. Skip the second and a chain gets bolted onto a product that never needed one.

1 / Job Name the action

Send, receive, lock, refund, issue, replay, prove, or settle: one verb, one person doing it often enough to care.

2 / Reason Say why a server won't do

Self-custody, public ordering, or proof that state wasn't rewritten in private. One has to be true.

What the app needsRouteWhy that one
Payment, receipt, balance, withdrawal, or support evidenceLive network workCurrent wallets, APIs, and accepted-transaction checks already handle this.
Vault, escrow, spend cap, asset rule, release, refund, or timeoutToccata covenants A bounded spend rule is simpler to build and audit than a full app runtime.
When to split into more than one covenant

If the product splits into states that never touch, use one covenant per state and the parallel work comes free.

One app keeps its own richer state from accepted Kaspa transactionsBased app or replay pathThe app proves or replays its own state without needing cross-app atomicity.
Each action needs its own proof, privacy check, or custom validity ruleInline ZKIt fits, and costs more proof and ops work than covenants or based apps do.
The claim depends on another chain, an oracle, a price, or a real-world eventName the anchor firstSource root, finality certificate, oracle, or challenge process. Pick one before writing proof code.
Many users mutate the same app state at onceFuture full vProgsBuild the narrow app first. Argent's Inter-Covenant Communication already shows separate covenant apps acting as one, so far only in unaudited offline demos.

Start a based app as deterministic replay of accepted transactions, and add ZK only once proofs, privacy, or bridge logic become the product edge.

Issuing a fungible token means building against KCC-0020, a draft standard with a permanent supply-split consequence its co-authors partly defend and partly call a wrong pattern still needing a spec fix, plus an admitted partial-conformance implementation, tracked in full on the KIP and KCC page.

A covenant can only inspect the transaction spending it, not the wider chain: no shared-state read.

Why there's no shared-state read, and who's already hit it

Reading shared on-chain state, a price, a pool balance, consumes it in the same breath, and Kaspa has no reference-input equivalent to Cardano, Ergo, or CKB's.

A builder raised the gap in the Kaspa Core R&D Telegram group on July 18, 2026, sketching a covenant DEX that needs a shared price board: six reactions, no reply, and no KIP yet says whether the fix belongs at L1 or in a future vProg.

What to build

Products, sorted by what they need

Six families need nothing but the live network, and they are the ones with users on them today.

Receipts and checkout

Invoices, tips, and withdrawals showing inclusion, confidence, and risk as three separate facts.

Self-custody tools

Address books, payment requests, and accounting exports for keys people hold themselves.

Support helpers

Splitting exchange delay from network delay, which is what most support tickets mix up.

Node and API monitors

Diff a public API against your own node, and flag a stale provider before users notice.

Proof pages

One page carrying user action, txid, source, status label, and current blocker.

Activity dashboards

Payments, mining, and spam pulled apart, so one raw count stops passing for a signal.

Six more open up once a spend rule is doing the work. The hard part is the gap between a good UI and a rule the network enforces: address generation, a synced node, Silverscript compilation, and explorer-visible outputs all have to work first.

Vault policies

Spend caps, delayed withdrawal, and a recovery key, enforced by the spend script itself.

Assurance funding

Funds release only once enough backers commit by the deadline. Miss it and refunds fire on their own.

Conditional escrow

Milestone payments, disputes, and refund paths, each step visible on-chain.

Controlled assets

Tickets, credentials, and redeemable claims, each with a transfer rule the holder can read.

Atomic market primitives

Swaps, auctions, and OTC flows, with script behavior staying bounded.

Games and state machines

Turn-based apps where player state, move routing, and settlement are separate steps.

Attach a user job to every build: a budget nobody can drain at once, an asset that moves only under a controller rule.

Evidence

Prove the claim before you post it

A reviewer believes a claim when six things check out. Write them in this order and the pitch writes itself.

Claim

The exact sentence a reader would repeat to a friend.

Status lane

Live, testnet-only, targeted, roadmap, research, or wrong. Pick the one true today.

Source

The strongest source for that lane, even when a weaker one is easier to reach.

Artifact

Something a stranger can check: txid, release, KIP, or command output.

User-visible result

What a wallet user, builder, or node runner can see right now.

Remaining blocker

Whatever stands between this and a wider public claim, named plainly.

Live means code merged and switched on at mainnet. Testnet-only means accepted transactions on TN10 or TN12 and nothing past that. Targeted means booked for a near-term release, roadmap means signed off with no date, and research means still being explored.

Merged code proves the code exists, not that the network runs it, and mixing those lanes in a public post turns a testnet demo into a mainnet rumor.

Advanced state-transition proof note

State-transition proof models follow one pattern: selected-parent root plus current root plus leaf write witnesses. That keeps validation local to the single transition. Clients never have to maintain the whole incremental SMT.

Protocol status traces to code, releases, and primary sources in Sources. To place a specific public claim in one lane, use the claims checker.

Verify yourself

Run the checks yourself

A wallet screen shows a balance and asks to be believed. A node, an RPC call, or a second explorer either agrees or doesn't. Climb the ladder when the situation calls for it: an explorer read, then a second API, then self-custody wallet software, then a node answering from chain state. A normal payment doesn't need every rung.

Mainnet commands change with releases. Check the source links before touching real funds.

Run a Rusty Kaspa node

Docker for the container route, Rust and Cargo for the source route. A node verifies chain state. It does not create or protect wallet keys.

docker pull kaspanet/rusty-kaspad:latest
mkdir -p ~/kaspa-data
docker run -d --name kaspa-node --restart unless-stopped \
  -v ~/kaspa-data:/app/data \
  -p 16110:16110 -p 16111:16111 -p 17110:17110 -p 18110:18110 \
  kaspanet/rusty-kaspad:latest

docker ps
docker logs --tail=80 kaspa-node

Source build, then the same node with UTXO indexing:

git clone https://github.com/kaspanet/rusty-kaspa
cd rusty-kaspa
cargo run --release --bin kaspad

cargo run --release --bin kaspad -- --utxoindex

Use --utxoindex when wallet or UTXO queries need indexed state. A node that hasn't finished syncing answers confidently and wrongly, so wait for sync.

Open the terminal wallet and RPC path

The terminal RPC and wallet runtime, from a checkout:

cd cli
cargo run --release

For every transaction read the address, amount, fee, and network before signing. Send a tiny amount first, then confirm the accepted txid through an independent source.

Enable a JSON WebSocket RPC endpoint

wRPC is off by default. It opens a WebSocket SDKs can query for node state, so bind it carefully on public machines:

cargo run --release --bin kaspad -- --utxoindex --rpclisten-json=default

Practice on testnet, then in the TN12 lab

cargo run --release --bin kaspad -- --testnet

cargo run --release --bin kaspad -- --testnet --netsuffix=10 --utxoindex

Check the current netsuffix, release, and flags against active docs first. The TN10 examples are Crescendo-era context; the Rusty Kaspa tn10-toc2 and tn10-toc3 pre-releases, plus the Testnet-10 REST status endpoint, are the Testnet-10 Toccata activation evidence.

TN12 is where covenant and replay experiments get tested before mainnet. The lab repo ships a results explorer and a playground:

git clone https://github.com/parker2017code/tn12-covenant-vault-demo
cd tn12-covenant-vault-demo
npm ci
npm run check:all
npm run check:tn12

Fund only the printed kaspatest: addresses, from a faucet that serves testnet-12. Every Kaspa testnet shares that prefix, so tKAS from a Testnet-10 faucet lands on a network TN12 never sees. Anything run with --submit broadcasts for real.

Hosted API checks

The Kaspa Developer Platform is a hosted API for chain data, transaction checks, and a node RPC proxy. It works for prototypes, dashboards, and second-source checks, not as a protocol source.

POST

Transaction acceptance

Batch-check txids for acceptance, block hash, and confirmation count.

curl --request POST \
  --url https://api.kas.fyi/v1/transactions/acceptance \
  --header 'Content-Type: application/json' \
  --header 'x-api-key: <api-key>' \
  --data '{"transactionIds":["<txid>"]}'
GET

DAA-score blocks

Read a bounded DAA-score range. KDP caps each request at 100 scores.

curl --request GET \
  --url https://api.kas.fyi/v1/blocks/daa-score/{daa_score_start}/{daa_score_end} \
  --header 'x-api-key: <api-key>'
GET

Address history

Large histories need cursor pagination. Cache results, or the requests pile up fast.

curl --request GET \
  --url 'https://api.kas.fyi/v1/addresses/<address>/transactions?limit=100' \
  --header 'x-api-key: <api-key>'
DATA

API data rules

Amounts arrive as sompi strings. The key goes in x-api-key, and a 429 means back off.

1 KAS = 100000000 SOMPI
amount: "31112708372"

The community REST API at api-tn10.kaspa.org is a separate trap: its submit schema (checked against the live openapi.json) never carried compute_budget, so SilverScript covenant deployments through it fail with "script units exceeded the amount committed in the input: used=100000, limit=9999." Submit straight to a kaspad node instead.

Before shipping

Checks that catch the expensive mistakes

  1. Pick network first. Mainnet uses kaspa:, TN12 uses kaspatest:, and reusing test keys for mainnet is how funds get lost.
  2. Use the right node. Testnet covenant work needs a build for that testnet. Mainnet builders run the released mainnet node.
  3. Check sync and UTXO index. An unsynced node or a missing index returns a balance that looks real and isn't.
  4. Separate UI policy from consensus rules. A wallet warning is not an enforced covenant. The chain doesn't know the UI exists.
  5. Record exact submit details. Log SDK version, node version, network id, endpoint, encoding, and tx version every time.

After submit, fetch accepted state and diff it against what the app claims happened. If they don't match, that's the bug report. Three results get read as the same result and are not: a transaction the network accepted, a local reject inside one machine's script engine, and a wallet-policy refusal the network never saw.

Open verification checklist
Builder habit Consequence Check
Fetch accepted state after submit Local construction proves a transaction was built. It doesn't prove the network accepted it. Record is_accepted, accepting block data, output script type, address, and amount.
Pin the submit surface REST, JSON wRPC, Borsh wRPC, SDK versions, and testnet branches can each hand back a different transaction shape for the same request. Log SDK version, node version, network id, endpoint, encoding, tx version, and input budget fields.
Compare with a known working spend Witness order, signature preimage, redeem-script shape, and constructor keys are far easier to debug against a sibling transaction that already worked than in isolation. Diff the failing path against an accepted release, refund, or simple payment path before blaming protocol rules.
Label failed attempts narrowly A tooling failure and a consensus failure look identical from the outside. They need different labels or the next builder repeats your mistake. Keep the artifact, but mark it as bad config, stale tooling, submit mismatch, or confirmed consensus rejection.

A prototype stays testnet-only until mainnet evidence says otherwise.

Infrastructure note

Some builders need Toccata prep work

Nodes, wallets, pools, exchanges, explorers, indexers, and custom RPC or protobuf code all need work before Toccata. Anyone building on top of those does not.

Nodes

Run Rusty Kaspa v2.0.1 or newer. The database upgrade only runs one direction, so a rollback means a full resync.

Fees

Direct RPC submission now runs on the standard-fee floor: 100 sompi * max(compute grams, 2 * transaction bytes) Compute grams price the script work a covenant runs on spend, on top of raw transaction bytes. A sompi is 1/100,000,000 of one KAS. . That's a mempool policy number, not a consensus rule.

APIs

New integrations need storageMass/storage_mass, transaction version 1, input computeBudget, output covenant, and UTXO covenant_id wherever those fields apply.

Indexers

No getUtxosByCovenantId RPC exists on mainnet or testnet-10. Every covenant project ships its own indexer; a concrete design has sat unanswered since August 4, 2026.

Service providers

Test deposits, withdrawals, mining templates, and fee estimation against Testnet-10, then against mainnet. The two won't match on every edge case.

Source: the Rusty Kaspa Toccata node setup guide. Miners pointing an ASIC at their own node have a separate path: mining Kaspa.

Order of work

Build wallets and payments first

Wallet and payment paths come first, then small covenant-shaped products, and based-app paths only once the product needs shared state. A product that signs transactions, holds funds, or promises uptime needs a node, an indexer, and a backup provider, not one hosted API.

Two open questions here have no shipped answer. If a user hands off an if-this-then-that strategy, nothing yet stops a miner or searcher from front-running the same event signal. And a validity proof big enough to be worth submitting trades block size against the standard-fee floor that keeps spam costly.
