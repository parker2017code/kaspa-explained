Kaspa builder funnel

Build on Kaspa without forcing the use case.

Start with the user job. Then choose the smallest Kaspa path that gives the product something useful: fast mined ordering, self-custody, public evidence, spend rules, commitments, or proof-backed state.

Status boundary: use current status and Toccata status before calling any app-layer capability live.

vProgs filter

Does the app need vProgs?

Most early Kaspa apps should not start by saying they need vProgs. Start with the smallest honest path, then move up only when the product requires richer app state or app-to-app composition.

App needBetter first routeWhy
Payment, receipt, balance, withdrawal, or support evidenceLive network workUse current wallets, APIs, nodes, txids, and accepted-transaction checks.
Vault, escrow, spend cap, asset rule, release, refund, or timeoutToccata covenantsA bounded spend rule is simpler than a full app runtime.
One app keeps its own richer state from accepted Kaspa transactionsBased app or replay pathThe app can prove or replay its own state without requiring cross-app atomicity.
A statement needs proof before settlementZK or proof-check pathUse proof verification for a specific statement, then define external anchors separately.
Several independent app states must succeed or fail togetherFuture full vProgsThis is the app-to-app composition case, and it remains roadmap until activation evidence exists.
