What's real here, and what's illustrative

The Argent lines are quoted from the Ticket transfer entry (the full listing is below, in the language model section) and from Argent's own README. Argent, Silverscript, and Kaspa Script all use require, and blake2b and checkSig are Silverscript builtins, documented in its tutorial with the identical call shape Argent uses. That is the real relationship for those two lines: Argent inherits Silverscript's expressions rather than reinventing them.

The become line is different. Argent's README says become routes "lower to output validation," and that an exact continuation into the same actor "can use cheaper script-public-key checks." Silverscript's own tutorial documents the named builtin for that job:

validateOutputState(int outputIndex, object newState)

used to "validate continuation into the same contract template." The Silverscript line shown for that step names this real, documented builtin and shapes it around the Ticket example's own fields. It is not a copy of Argent's actual generated .sil output for this contract, which neither repository publishes.

Past Silverscript, compilation reaches Kaspa Script: silverc's own docs describe its compiled JSON output as carrying a bytecode field, "the compiled bytecode (as an array of bytes)." No file in either repository shows that array disassembled into opcode names for a real example, so this demo doesn't invent one. Argent's own README states the project "is still under active development and is not yet release-ready," waiting on Silverscript's audit, then its own.

The gap it fills

A covenant is opcodes. An application is several agreeing.

A covenant is a rule attached to a coin, written as raw opcodes; hand-auditing a multi-contract application in those opcodes is not realistic for most teams. Argent, not officially blessed by the protocol team, works that gap: an actor is a covenant object a transaction consumes and recreates, and the compiler turns a readable description into enforced script.

Inter-Covenant CommunicationSeparately compiled covenant apps joined into one all-or-nothing transaction, so either every part lands or none does. It works on Toccata today, in unaudited offline demos only. What vProgs would add on top is shared mutable state, which ICC does not provide. lets an actor from one compiled app observe or authorize an actor from another inside a single transaction, so separately built apps succeed or fail together. Open the language model and a worked example

On an account chain, a contract sits at an address and receives calls. On Kaspa there is no such thing to call. There are only outputs, and a covenant is a rule about what the next output has to look like. Argent takes that constraint seriously instead of hiding it.

Four ideas carry the core, and they are not the whole surface: the documented set is eight, adding delegate, consumes, and emits, with the route machinery sitting behind those.

A state is a typed record. An actor owns one. An entry is a way to spend that actor, taking arguments and declaring which actors it emits. And become names the successor the transaction creates.

state TicketState {
    byte[32] owner;
    int units;
}

actor Ticket owns TicketState {
    entry transfer(byte[32] next_owner, sig owner_sig, pubkey owner_pk) emits next: Ticket {
        require(blake2b(owner_pk) == owner);
        require(checkSig(owner_sig, owner_pk));
        require(next.value == self.value);

        TicketState new_state = {
            owner: next_owner,
            units: units,
        };

        become next <- Ticket(new_state);
    }
}

app Tickets {
    actor Ticket;
}

Nothing here is a call to a contract. The transaction spends the old ticket and creates the new one, and every require is a condition the script engine checks before it will let that happen.

If a condition fails, the transaction is invalid. There is no revert, no gas refund, and no partially applied state, because there was never a running program to interrupt.

What the compiler outputs

The compiler emits three things for each build, and every one is inspectable without rebuilding the project: artifact.json as the portable description, manifest.json as build metadata, and the rest as ordinary .sil Silverscript contracts. Those contracts use no covenant macros and compile like any other Silverscript, which matters for review: an auditor reads generated script, not a black box.

An argentc inspect command reports script and state sizes, static opcode counts, entry arguments, route metadata, and signature-script size estimates without rebuilding. The design targets script composition primitives such as OP_CAT and OP_SUBSTR, transaction introspection, and consensus-supported covenant identities, which is KIPKaspa Improvement Proposal: the process that specifies, reviews, and merges a protocol change. Nothing on this site counts as shipped without a merged KIP and a release tag.-20, the piece Toccata carried to mainnet.

What's proven, what isn't

Partitioned state works. Shared state is a design direction.

Every example partitions cleanly: one UTXOUnspent transaction output. Value sits in separate coins, spent whole and replaced by new ones, instead of living in one account balance that gets edited. per ticket, per game, per position. Shared mutable state, most of what people mean by DeFi, has no public Argent implementation yet.

The README's caution is real, and so is its list of working pieces; quoting only one half gets it wrong. Anyone describing Argent applications as running on Kaspa mainnet today is describing something that has not happened.

Open the evidence: the DEX example, commit history, and the README quoted in full

The playground's DEX is a single pair, and the compiler's own SECURITY.md never mentions replicas, keepers, or bounded divergence, the shape a partitioned pool would need.

Three repositories, and one person writes nearly all of it. As of mid-August, Michael Sutton held 73 of the compiler's 77 commits, and 58 of those landed in July, when the project moved out of his personal namespace into an argent-lang organization. The compiler is up to 78 commits as of August 17, 2026, syncing generated output with Silverscript's own August changes; the per-author split was not rechecked at the new count.

The README's caution is real: "The project is still under active development and is not yet release-ready," a production path opens only "Once Silverscript completes its audit and is released," and Argent "will still need further audit and hardening before general production use."

The second half names what that caution is about: "The main pieces are present: compiler, generated Silverscript, portable artifacts, runtime transaction building, multi-actor routing, cross-app linking," and five more. That is a list of things that work, not things planned.

The gate is a review queue, not a construction site: an audit on Silverscript, then a release, then an audit on Argent. Until then the README points at advanced users who can read the generated .sil themselves.

Silverscript recommends its bytecode artifact only on testnet-10. Kaspa's Argent chapter is more cautious again, calling it "a design direction and prototype, not a production-stable API." That reads as the ecosystem's conservative floor, not the project's current state: Kaspa's own chapter still links the old repository path.
