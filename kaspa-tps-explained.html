Throughput

Kaspa TPS, explained.

There is no single Kaspa TPS number. Simple payments run roughly 2.5k to 3.4k TPS at 10 BPS, and covenant apps, ZK settlements, and future vProg-style systems each run their own math against a different bottleneck.

Status checked July 25, 2026: Kaspa mainnet runs the Crescendo-era 10 BPS network. Toccata activated at DAA 474,165,565 and changed proof and covenant capacity. Ordinary payment TPS tracks the 10 BPS network and transaction mix.

Simple payments

Current simple-payment capacity

Kaspa mainnet produces ten blocks per second. The shared block mass limit in current mainnet parameters is 500,000, which sets a budget of 5,000,000 transaction mass per second before policy, fees, propagation, storage shape, and real mempool behavior enter the picture.

A signed ordinary P2PK-style 1-input, 1-output payment costs roughly 1.6k mass by the code's conservative arithmetic. Add a change output and a 1-input, 2-output payment runs closer to 2.0k mass. Divide the block budget by those shapes and the count lands around 250 to 300 simple transactions per block: the mid-2k to low-3k TPS lane at 10 BPS. Leaner shapes and rounding push the upper end to the commonly cited 3.4k TPS.

Benchmarks built on artificial minimum-size transactions score higher than that. They are measuring a lab envelope, and a real signed payment is heavier than the transactions in those runs.

Mass model

Mass is the real limit

A raw count of transactions per block hides Kaspa's real limit: mass. The implementation charges for serialized bytes, script-public-key bytes, signature-operation or compute-budget work, transient byte mass, and storage mass effects. A larger transaction eats a larger slice of the block budget regardless of how the mempool counts it.

App transactions change the footprint. More inputs, more outputs, larger scripts, covenant metadata, payload data, proof bytes, or state-transition evidence all crowd out simple transfers competing for the same mass budget. Node-side repeated work moves the ceiling further: validation cost, propagation size, UTXO access patterns, storage effects, and app-specific indexing.

Payload data has its own bound. Kaspa's docs put the payload ceiling around 25 KB when payload data dominates a standard transaction, because the standard transaction mass ceiling and transient byte accounting still apply on top of it.

Toccata

What Toccata changes

Toccata doubles the transient mass budget without touching the payment-relevant limit. It is mainly a programmability upgrade: it changes what Kaspa L1 transactions can express and verify, covenant-style spending rules, covenant IDs, ZK verifier infrastructure, sequencing-commitment access, and the first base-layer foundations for based-ZK apps.

The Toccata guide and current params show one throughput-relevant change: transient mass rises from 500,000 to 1,000,000 at activation, while the compute and storage reference limit holds at 500,000. The guide frames the increase around fitting STARK-sized proofs. Toccata also adds v1 transaction fields such as output covenant data and input compute commitments, and raises the standard minimum relay fee.

Covenants and assets

Covenant transactions run heavier

One token transfer in your wallet can cost several times the mass of a plain payment. A covenant transaction carries rules about how its coins or state can be spent next, which is what makes vaults, escrow, assurance contracts, controlled assets, and token-like rules possible. That structure costs more than a simple payment.

You see one action. The L1 footprint depends on the asset rule underneath it: covenant state, covenant IDs, authorization rules, extra outputs, witness data, app payloads, or indexer-readable state. Counting that transaction as equivalent to an ordinary payment understates how much of the block it consumes.

Simple-payment TPS is a payment metric. Covenant-app throughput needs its own count, built from the actual transaction shape and state pattern.

ZK proofs

ZK changes the metric

One L1 transaction can settle thousands of off-chain actions. ZK proof systems move app execution off the base layer and keep a compact verification path on L1: a single proof or settlement transaction updates an app commitment after many off-chain actions run. The L1 transaction count stays small while the app action count grows large.

That does not make TPS unlimited. Effective app throughput is bounded by the app, proof system, batch size, proof size, proving hardware, proof-generation time, data availability, settlement cadence, exit rules, and bridge/oracle assumptions. A ZK proof proves a statement about chosen inputs. External facts still need an anchor: a light client, finality certificate, accumulated-work view, reporter set, oracle, or challenge process.

The metric that matters for a ZK app is app actions per settlement cycle, with L1 proof verification as the bottleneck. That number can run far above L1 transaction TPS for a single app, and it is still bounded by proof economics and state design.

vProgs

vProgs remain roadmap architecture

Toccata ships the parts vProg-style systems need without shipping vProgs: covenants, proof checks, covenant IDs, and partitioned sequencing commitments. Full vProgs are a later architecture for app programs that prove richer logic while sharing Kaspa ordering.

KIP-21 stops every prover from having to follow the entire DAG for every app. Its partitioned commitment design targets O(activity) proving: a prover for one app lane tracks only that lane's activity. Current parameters cap user-lane churn at 50 non-coinbase lanes per block and 1,000,000,000 gas per lane. At 10 BPS, that is a worst-case bound of 500 user-lane updates per second. User transaction throughput still needs its own transaction-shape assumptions on top.

The public kaspanet/vprogs repository shows the implementation direction: resource access, scheduling, batches, state diffs, transaction runtime, L1, and ZK components. Michael Sutton's Argent repo is related tooling research for composing multi-contract covenant apps into Silverscript. Neither repo is mainnet activation evidence for full vProgs.

Checklist

How to talk about Kaspa capacity

Workload

Name whether the number covers simple payments, covenant spends, token rules, proof settlements, or app actions.

Transaction shape

List inputs, outputs, scripts, payload, covenant fields, proof bytes, and storage effects.

Block assumptions

State BPS, block-mass limits, standardness limits, fee policy, and mainnet versus testnet context.

App/proof design

For ZK and vProg-style systems, state batch size, proving cost, settlement cadence, state access, and exit design.
