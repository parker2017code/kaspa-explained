Kaspa Toccata explained

Crescendo made 10 BPS live. Toccata is live too: the hard fork that adds covenants, covenant IDs, ZK proof checks, sequencing lanes, and based-app foundations, all without turning Kaspa into an EVM.

Activated: Rusty Kaspa v2.0.1 is the current Toccata release. v2.0.0 set mainnet activation at DAA score 474,165,565, and mainnet crossed it June 30. See Toccata status for what's checked since.

Direct answer

What Toccata changes

KIP-17

Covenant scripting lets a UTXO inspect the spending transaction and constrain what the next output must look like.

KIP-20

Covenant IDs give covenant state a consensus-tracked lineage, so a fake lookalike state can't be conjured out of thin air.

KIP-16

ZK verification lets a script check selected proof systems instead of asking L1 to run every app step itself.

KIP-21

Sequencing commitments let an app prove its own lane of activity; without them, it would have to prove that almost the entire DAG is irrelevant to it.

Based apps

Apps can anchor state to Kaspa ordering, commitments, settlement, exits, or proofs without relying on an independent sequencer.

vProgs

Full vProgs are separate, later architecture for richer app execution and cross-app composition. They are not part of what activated.

Design frame

It is not an EVM turn

Toccata does not make Kaspa an account-based global virtual machine. Kaspa still uses UTXOs: transactions spend specific outputs and create new outputs. The consumed and created state sits right in the transaction. No shared global account layer sits behind it.

The design target is narrow: add enough rule expressiveness for money flows while keeping the base layer lean. A covenant can say, for example, "this next output must preserve the rule," "this spend needs a controller input," or "this refund path opens after the timeout." The app logic lives in constrained UTXO transitions, proofs, or app-side execution anchored back to L1.

Toccata is an expressiveness upgrade. It expands what L1 transactions can enforce and verify, without migrating Kaspa to a different platform. Mature wallets, DeFi liquidity, audits, custody flows, and full app composition are separate claims that still need their own evidence.

Covenants

Spend rules become state rules

A normal payment proves the spender is allowed to move funds. A covenant-style spend can also inspect the spending transaction and require the next output to preserve a rule. That turns a UTXO into a small state machine: the coin moves, but the rule keeps going.

KIP-17 adds the script tools for transaction introspection, byte manipulation, hashing, signatures from stack, and ZK precompile access. KIP-20 adds covenant IDs, so a covenant family carries a stable 32-byte identity through valid continuations. Together, they make stateful UTXO rules easier to inspect and harder to fake.

ZK apps

Proofs move computation off L1, then settle back

One proof can stand for many off-chain app actions, if the app is designed that way. A proof transaction may weigh more than a simple payment, but the L1 transaction then serves as a settlement or verification event rather than the computation itself.

KIP-16 introduces OpZkPrecompile with initial Groth16 and RISC0-Succinct paths, letting a script verify a proof about chosen public inputs. The proof still needs a defined statement, an app design, and an anchor for outside facts. ZK does not prove prices, bridge truth, game integrity, or real-world events unless the inputs and trust boundary are defined first.

That's why "Kaspa TPS" needs a workload label attached. Payment TPS, covenant transaction capacity, proof-settlement capacity, and effective app actions per settlement cycle are four different measurements.

KIP-21

Sequencing without proving the whole DAG

Based apps use Kaspa L1 ordering. A naive design gets expensive fast: every app would need to prove which L1 transactions were for it and which weren't. At scale, proving what isn't yours turns into the real burden, crowding out the useful work.

KIP-21 fixes that with partitioned sequencing commitments. A prover for one app lane follows that lane's activity, so proving cost tracks the app's own activity instead of the whole DAG's.

That gives based apps and later vProg-style systems a way to skip proving unrelated network activity. It is not proof that full synchronous app composition runs today: that's still separate, later work.

vProgs boundary

Based apps first, full vProgs later

The public kaspanet/vprogs repo describes an early Rust framework for based computation on Kaspa, with core, storage, state, scheduling, transaction runtime, node, L1, and ZK pieces. It's research and roadmap work that shows the implementation direction only; it hasn't shipped as software.

Michael Sutton's Argent repo is related research tooling: an actor-style frontend that aims to generate Silverscript for multi-contract covenant systems. It names the real developer-experience problem directly: writing many linked covenant contracts by hand is the hard part.

Toccata, activated, supports covenant apps, proof-gated flows, sequencing commitments, and standalone based-app foundations. Full vProgs are separate, later, roadmap architecture for richer execution and cross-app composition. It hasn't reached testnet yet.

Standard fee floor

Operator changes

Toccata changes standard fee policy for direct RPC submission to 100 sompi * max(compute grams, 2 * transaction bytes). Mempool policy and consensus stay separate rule sets, which is why consensus-valid zero-fee transactions are still possible while an upgraded node can reject an underpriced standard transaction from relay or RPC by policy. The per-audience upgrade steps, for node operators, wallets, exchanges, miners, and pools, are on Toccata status.

The byte-size change is tied to proof support. The guide points to the doubled transient-mass limit as the reason hardware specs changed, specifically to allow ZK-STARK proofs. That's proof-transaction capacity work, and it expands the size envelope those transactions need. Ordinary payment-throughput claims need their own, separate assumptions.

Mining

Rust Stratum Bridge: point your hardware at your own node

ASIC miners speak Stratum. Kaspa nodes speak Kaspa RPC. The Rust Stratum Bridge gives miners and pools a maintained path for connecting mining hardware to an upgraded Kaspa node through the Rusty Kaspa stack.

Miners and pools need to preserve post-Toccata block-template fields and test their mining flows against them. A miner who can point hardware at their own node depends less on a pool interface to reach the network at all.
