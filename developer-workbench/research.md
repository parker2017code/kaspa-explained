# Kaspa developer workbench: ecosystem baseline

Checked 2026-09-09 against primary repositories and project pins. This is an integration guide, not an audit or a claim that two projects interoperate.

## Recommended beta baseline

- Keep the workbench's node and browser transaction baseline on **Rusty Kaspa / WASM SDK v2.0.1**. It is the current stable release, and the `stable` branch points to its commit, `cfafeb4`. Use `master` only for an explicitly labelled experiment.
- Keep existing contracts on **SilverScript v1-rc1 (`c7d17a1`)**. It is still a release candidate. Three later `master` commits add resource-limit validation and ABI metadata; test those changes in isolation before considering a pin update.
- Keep existing Argent artifacts on **`d08e52d`**. Argent has no release or tag and says it is not release-ready. Its one later `master` commit adds state-vector and slice conversions; generated SilverScript and artifacts must be rebuilt and reviewed before any upgrade.
- Treat **KRC-20/KRC-721 data as indexer data**. A Kaspa node validates the underlying transactions, while a Kasplex-compatible indexer interprets inscription payloads and reconstructs token state.
- Capability-detect wallet methods. There is no confirmed ratified common wallet API in the official KIP index. The independent Kaspa Wallet Standard v0.2 is useful design input, but its own text says standardization is still in progress.

## Protocol boundary the UI must preserve

Native covenants and KRC assets both use Kaspa transactions, but they establish different facts:

1. Rusty Kaspa consensus validates transaction structure, scripts, covenant IDs, authorization links, and covenant state transitions.
2. SilverScript compiles readable covenant rules to Kaspa Script. Argent compiles multi-actor application descriptions to SilverScript plus runtime artifacts. Neither creates a separate token index.
3. KRC protocols encode operations in commit/reveal transaction payloads. A KRC indexer applies the protocol's ordering and accounting rules to derive deployments, mints, transfers, and balances. Ordinary Kaspa nodes do not enforce KRC ticker uniqueness, supply, or account balances.
4. A wallet may display or construct both native covenant and KRC operations, but that is product-level support. It does not make the formats interchangeable. Any migration or bridge needs its own specified transaction flow, indexer behavior, covenant rules, and end-to-end evidence.

## Sources and evidence limits

Repository release/tag metadata, branch heads, source documentation, and the local pins were checked on 2026-09-09. Release status does not establish an audit, mainnet suitability, wallet adoption, or cross-project interoperability. The workbench should show `stable`, `release candidate`, `development`, `indexer`, and `draft` as distinct states.
