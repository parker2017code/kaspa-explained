KIPs and KCCs

Two separate processes decide what Kaspa becomes. One changes the protocol, one does not. This page reads both straight from their repositories, so what you see is the current state rather than a label somebody typed once.

A Kaspa Improvement Proposal changes consensus, node behavior, or a client API, and ships when implemented and activated. A Kaspa Call for Conventions is the opposite: an agreement between builders about how to encode a token, name a field, or shape an ABI, with no consensus change. The KCC README draws the line itself: "KCCs do not propose changes to Kaspa consensus or core-node behavior." A merged KIP marked Active is protocol law; an open KCC pull request is a draft people are still arguing about.

Conventions

Kaspa Calls for Conventions

Builder agreements on encoding, not protocol changes: three merged, all still marked draft.

The KCC repository was created on July 15, 2026. Three specifications have merged into it: KCC-0001, KCC-0002, and KCC-0020. Each one's own document header still reads Status: Draft.

A merged file in this repo is a checked-in draft, not an adopted standard: the README's own bar for acceptance is a Comments-URI discussion window and consensus among implementers, and none of the three has cleared that.

KCC-0001 defines the byte layout for a covenantA rule attached to a coin that the network itself checks on every spend, not a server's promise., a rule attached to a coin that these tokens sit on. The covenant breaker demo attacks a vault covenant with an early withdrawal, a skipped recovery key, and a forged lookalike, and shows the exact rule that stops each one.

The two open pull requests both claim adoption evidence the repository itself does not carry: KCC-0021's author says kascov and the wallet KaspaRocket already use its metadata convention, and KCC-0402's author says a reference implementation, k402, has payment-channel transactions live on mainnet. Neither claim is independently confirmed; treat both as the author's word until a merge or an outside source backs them.

The four-digit repository numbering is canonical; forum shorthand like "KCC20" is not the identifier in the repository, and nothing has been ratified. KCC-0020 is the most argued-over thread on the builder forum, and its shape has already leaked into working code: the Argent compiler ships a kcc20_asset.ag example defining a transferable asset covenant. That is normal before acceptance, not acceptance itself.

A token issued against KCC-0020 today inherits three known defects: a permanent supply-split consequence its co-authors partly defend and partly call a wrong pattern still needing a spec fix, one production deployment that admits partial conformance, and a launchpad already on its fourth incompatible template.

Common question: what happens when a token standard splits supply?

Under KCC-0020, updating some holders' cells and not others while a supply-wide commitment changes splits the token into groups that can never consolidate again, permanently. The spec's own co-authors are on record disagreeing about which uses of that mechanism are intended versus a bug; the full record is below.

The supply-split consequence, defended in part, conceded in part

Issue #14, opened August 21, 2026 by Knitser and still open, shows that KCC-0020's transfer consolidation rule requires every input to carry the same extended-state commitment, but its state-update entrypoint can only be authorized by each cell's own holder, not the issuer, so there is no way to move every holder's cell to a new commitment at once. Update some cells and not others and the token's supply splits into groups that can never consolidate again, permanently. Co-authors Manyfestation and Michael Sutton defend one version of this as intended: Sutton's own stablecoin-blacklist example, where a frozen flag deliberately "renders the token as temporarily non fungible." But Sutton then flagged a second pattern, extended state used for ephemeral, receipt-like data that mutates without affecting fungibility, as "a wrong pattern," and both co-authors agreed it should either be defined in the standard or moved out of state entirely. A fourth commenter, ShawnPearce, added on August 23, 2026 that the standard's other candidate home for that data, the transaction payload, has its own catch: the v1 sighash commits the payload unconditionally, so it is signature-bound and transaction-scoped rather than per-cell, and under this spec's borrowed receive, a borrower who signs the transaction controls the payload the owner's cell gets recreated with. Knitser has not withdrawn his original concern, and no spec change has merged.

The one production implementer's own conformance admission

Issue #11, opened July 26, 2026 by KaspaCom, is the only production implementer of a KCC token standard stating its own conformance level in writing: KaspaCom's deployed KCC20V2 "should be described as partially aligned, not fully conforming" with KCC-0001, 0002, 0020, and 0021. KaspaCom closed the issue itself on August 22, 2026, after the KCC-0021 author explained that its metadata layer is deliberately behavior-independent and does not require byte-for-byte KCC-0020 conformance to adopt. That answers KaspaCom's question; it does not withdraw the partial-conformance statement on the record above.

The launchpad already forking its own template four times

The standard's own template shape is already fragmenting on mainnet: one launchpad's 74 live tokens span four separate template generations, with no migration path between them, only opt-in burn and reissue, according to a kas-smiths.org post from 0xKnitser on August 15, 2026.

A second open gap in the same spec: borrowed receive

Shawn described it on the kas-smiths.org forum, July 10, 2026: "borrowed receive lets anyone change your UTXO's outpoint, which griefs pre-signed, outpoint bound transactions." Borrowing a token into a UTXO before a pre-signed spend lands invalidates the transaction and forces a rebuild, with no signature-level fix. A month later Shawn explained why: "the v1 sighash folds the spent input's own outpoint into the signed message unconditionally," and AnyoneCanPay "only zeroes the other inputs' outpoints, never the signed input's own." Authorization has to move to something the covenant checks against its own state, not the transaction signature; nothing has merged.

KCC-0021, the covenant token metadata standard, is why the same forum keeps citing image URLs going dead: covenant tokens have no metadata standard on mainnet without it, so name, ticker, and image all live off-chain today. 0xKnitser cross-checked one live launchpad's logos on August 15, 2026 and found 5 of 19 dead within days, 3 more serving HTML instead of an image. KCC-0021 stays an open, unmerged pull request.

Read the KCC repository, or follow the discussion on kas-smiths.org.

How this page stays honest

Where these numbers come from

Both tables above are written into the page as a baseline, verified by hand on the date stamped under each one. When the page loads it asks the two repositories for their current state and replaces the baseline if anything moved. If GitHub is unreachable or rate-limits the request, the baseline stays and the stamp says so; nothing here is generated from memory.

A status word here is evidence of where a document sits in a process, never that something works. For what is actually running, use the live status page; for activated versus usable, see what still has to be built.
