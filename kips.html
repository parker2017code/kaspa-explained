KIPs and KCCs

Two separate processes decide what Kaspa becomes. One changes the protocol, one does not. This page reads both straight from their repositories, so what you see is the current state rather than a label somebody typed once.

A Kaspa Improvement Proposal changes consensus, node behavior, or a client API. It ships when it is implemented and activated. A Kaspa Call for Conventions is the opposite: an agreement between builders about how to encode a token, name a field, or shape an ABI, with no consensus change at all.

The KCC README draws the line itself: "KCCs do not propose changes to Kaspa consensus or core-node behavior. Such changes belong in Kaspa Improvement Proposals (KIPs)."

The two get confused constantly. A merged KIP marked Active is protocol law. An open KCC pull request is a draft one person wrote and others are arguing about, and calling it a standard is how people end up building against something that never lands.

Conventions

Kaspa Calls for Conventions

The KCC repository was created on July 15, 2026. Three specifications have merged into it: KCC-0001, KCC-0002, and KCC-0020. Each one's own document header still reads Status: Draft.

A merged file in this repo is a checked-in draft, not an adopted standard: the README's own bar for acceptance is a Comments-URI discussion window and consensus among implementers, and none of the three has cleared that.

KCC-0001 defines the covenant byte layout these tokens sit on. The covenant breaker demo attacks a vault covenant with an early withdrawal, a skipped recovery key, and a forged lookalike, and shows the exact rule that stops each one.

The two open pull requests both claim adoption evidence the repository itself does not carry. KCC-0021's author says the reader implementation kascov and the wallet KaspaRocket already use its metadata convention. KCC-0402's author says a reference implementation, k402, has payment-channel transactions live on mainnet.

Neither claim could be confirmed independently; treat both as the author's word until a merge or an outside source backs them.

The four-digit repository numbering is canonical. Forum shorthand like "KCC20" is convenient and is not the identifier in the repository, which matters when someone claims a token already follows a ratified standard. Nothing has been ratified.

KCC-0020 is the one to watch. It is the most argued-over thread on the builder forum, and its shape has already leaked into working code: the Argent compiler ships a kcc20_asset.ag example defining a transferable asset covenant whose owner can be either a public key or a covenant ID.

A convention appearing in a compiler's test suite, or in a merged draft file, before it is accepted is normal, and it is not acceptance.

Anyone weighing whether to issue a token against this draft is asking the right question: what breaks later.

A token issued against KCC-0020 today inherits three known defects: a permanent supply-split consequence its co-authors partly defend and partly call a wrong pattern still needing a spec fix, one production deployment that admits partial conformance, and a launchpad already on its fourth incompatible template.

The supply-split consequence, defended in part, conceded in part

Issue #14, opened August 21, 2026 by Knitser and still open, shows that KCC-0020's transfer consolidation rule requires every input to carry the same extended-state commitment, but its state-update entrypoint can only be authorized by each cell's own holder, not the issuer, so there is no way to move every holder's cell to a new commitment at once. Update some cells and not others and the token's supply splits into groups that can never consolidate again, permanently. Co-authors Manyfestation and Michael Sutton defend one version of this as intended: Sutton's own stablecoin-blacklist example, where a frozen flag deliberately "renders the token as temporarily non fungible." But Sutton then flagged a second pattern, extended state used for ephemeral, receipt-like data that mutates without affecting fungibility, as "a wrong pattern," and both co-authors agreed it should either be defined in the standard or moved out of state entirely. Knitser has not withdrawn his original concern, and no spec change has merged.

The one production implementer's own conformance admission

Issue #11, opened July 26, 2026 by KaspaCom, is the only production implementer of a KCC token standard stating its own conformance level in writing: KaspaCom's deployed KCC20V2 "should be described as partially aligned, not fully conforming" with KCC-0001, 0002, 0020, and 0021.

The launchpad already forking its own template four times

The standard's own template shape is already fragmenting on mainnet: one launchpad's 74 live tokens span four separate template generations, with no migration path between them, only opt-in burn and reissue, according to a kas-smiths.org post from 0xKnitser on August 15, 2026.

The supply split demo lets you issue a token, roll it out unevenly, and watch the supply fracture into groups that can never consolidate again, the unresolved tradeoff behind issue #14 made tangible.

A second gap sits in the same spec: borrowed receive. Shawn described it on the same forum thread, July 10, 2026: "borrowed receive lets anyone change your UTXO's outpoint, which griefs pre-signed, outpoint bound transactions." Borrowing a token into a UTXO before a pre-signed spend lands invalidates the transaction and forces a rebuild. There's no signature-level fix.

Shawn explained why a month later: "the v1 sighash folds the spent input's own outpoint into the signed message unconditionally," and AnyoneCanPay "only zeroes the other inputs' outpoints, never the signed input's own." Authorization has to move to something the covenant checks against its own state, not the transaction signature; nothing has merged.

KCC-0021, the covenant token metadata standard, is why the same forum keeps citing image URLs going dead: covenant tokens have no metadata standard on mainnet without it, so name, ticker, and image all live off-chain today.

0xKnitser cross-checked one live launchpad's published logos on August 15, 2026 and found 5 of 19 dead within days, and 3 more serving HTML instead of an image.

KCC-0021 stays an open, unmerged pull request.

Read the KCC repository, or follow the discussion on kas-smiths.org.

How this page stays honest

Where these numbers come from

Both tables above are written into the page as a baseline, verified by hand on the date stamped under each one. When the page loads it asks the two repositories for their current state and replaces the baseline if anything moved, then says when it last checked.

If GitHub is unreachable or rate-limits the request, the baseline stays and the stamp tells you it is a baseline. Nothing here is generated from memory.

A status word on this page is never evidence that something works. It is evidence of where a document sits in a process. For what is actually running on mainnet, use the live status page, and for the difference between a primitive being activated and an application being usable, see what still has to be built.
