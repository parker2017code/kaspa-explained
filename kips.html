Proposal tracker

KIPKaspa Improvement Proposal: the process that specifies, reviews, and merges a protocol change. Nothing on this site counts as shipped without a merged KIP and a release tag.s and KCCs

Two separate processes decide what Kaspa becomes. One changes the protocol, one does not.

A Kaspa Improvement Proposal changes consensus, node behavior, or a client API, and ships when implemented and activated.

A Kaspa Call for Conventions is the opposite: an agreement between builders about how to encode a token, name a field, or shape an ABI, with no consensus change. Its README draws the line itself: "KCCs do not propose changes to Kaspa consensus or core-node behavior."

A merged KIP marked Active is protocol law. An open KCC pull request is a draft people are still arguing about.

A margin fixed in advance, against one that tracks the network

A marginHow many blocks arriving at once a side tolerates before treating one of them as an attack. The DAG KNIGHT paper writes it k. is how many blocks arriving at once a network tolerates before one looks like an attack. Too low and honest blocks get rejected. Too high and the worst-case wait grows.

10 blocks per second (Kaspa mainnet's Crescendo-era rate) Runs past mainnet's rate on purpose. rusty-kaspa ships a lookup table that stops at 32 blocks per second. The formula behind it runs at any rate; the table is the limit, not the math. Push λ up while D stays fixed and PHANTOM's own confirmation time under attack grows exponentially in the paper's own bound, the harder reason to stop, not a shrinking security threshold: that decay is Nakamoto Consensus's problem, not PHANTOM's.
Assumed worst case: 5.0 s (mainnet's real setting) → margin needed: 124 (mainnet's real margin) 5 s is rusty-kaspa's own NETWORK_DELAY_BOUND constant (consensus/core/src/config/constants.rs, checked 2026-08-25). KIP-14, the Crescendo hardfork, sets D = 5, δ = 0.01 and states the resulting margin is "recalculated to be 124." Neither number is a choice this page made; both are what mainnet runs today.
0.5 s (margin this actually needs: 18) Not a measured figure. Where these numbers come from

Both rows are guarantees, not observations. Each is the DAG KNIGHT paper's own no-visible-attack bound (§1.5.2), computed at a stated 1% error tolerance (ε = 0.01). It carries no unspecified constant.

At a fixed 2 s delay it gives 12 s at 1 block per second, 43 s at 10, and 402 s at 100, a 9.3× increase that lines up with Sompolinsky's "tens of seconds at least, about 8x long."

What this costs

Not shipped, not parameter-free, efficiency unsolved.

Caveats and sources
  • Not shipped. Mainnet runs GHOSTDAG. KIP-2 is Status: Proposed; the dagknight branch is active, unmerged development on kaspanet's own repo, most recently "Merge branch 'dk-umc-proposed' into dagknight" on August 14, 2026. Still no testnet, no activation date.
  • Not actually parameter-free. The paper still requires a client-set bound D, and D must cover the latency an attacker could cause, not what the network is currently showing (Pass-Shi, Theorem 14). A calm network does not license a low D.
  • A visible attack does not slow down every payment. As long as a transaction has no visible conflicting spend, its ordering is commutative with recent transactions, so it can still confirm on the optimistic timeline above even while the pessimistic case is playing out elsewhere in the DAG (§4, footnote 14).
  • Efficiency is unsolved. KIP-2 itself lists the current DAGKnight pseudocode as "highly inefficient" and its rewrite as unfinished work, a stated reason this is still research four years on.
  • The ceiling of 32 blocks per second belongs to GHOSTDAG, not to DAGKnight. rusty-kaspa's Bps<BPS>::ghostdag_k() is a hardcoded match on precomputed values for 1 through 32. Past that the fallback arm reads panic!("see gen_ghostdag_table for currently supported values") (consensus/core/src/config/bps.rs, checked 2026-08-22).
  • Which is why the slider keeps going. GHOSTDAG needs a k chosen in advance for a given rate, so running it past 32 means a developer computes a new k and the network hard-forks. Nothing today defines one there. Removing that a priori k is KIP-2's whole premise, so DAGKnight has no table to run out of.
  • The upper end of that range is not a target. KIP-2 lists the optimal block rate as open research and recommends no number. The widely repeated "100 blocks/sec, netsplit-resilient" figure traces only to kaspa.org's marketing pages, unconfirmed by any KIP, release, or core-contributor statement.
  • No published cost figure exists, but the efficiency work is real. Contributor coderofstuff (40 commits to kaspanet/rusty-kaspa) builds the UMC-voting redesign on personal fork branches, then merges it into kaspanet's own dagknight branch. The dk-umc-proposed branch merged in on August 14, 2026, identical commit and all.
  • The write-up explaining it is not kaspanet's. It names the bottleneck behind KIP-2's "highly inefficient": the paper's recursive UMC-voting algorithm at O(n squared) worst case, with an O(n times K) amortized replacement proposed. That write-up lives on an unofficial personal wiki. The code is real engineering inside the project's own repo, unmerged to master and not adopted as the shipped algorithm.
Model, formula, and citations

GHOSTDAG's k comes from rusty-kaspa's own derivation, reproduced exactly here: k = min k̂ such that P(anticone > k̂) < δ, computed from x = 2·D·λ (D = assumed max delay in seconds, λ = blocks/second) via a Poisson-tail sum.

Mainnet's constants are NETWORK_DELAY_BOUND = 5s and GHOSTDAG_TAIL_DELTA = 0.01 (consensus/core/src/config/{constants,bps}.rs). At λ = 10 blocks/s and D = 5 s that gives k = 124, matching the compiled table in bps.rs exactly: 1 bps → 18, 2 → 31, 5 → 67, 10 → 124.

Does raising the block rate lengthen confirmation under GHOSTDAG? The paper says so directly (§1.2): "many blocks are created in parallel, blocks suffer from larger anticones, and transactions take longer to confirm," adding that "Kaspa's convergence time remains in the order of tens of seconds even when its latency is way below 10 seconds."

The guarantee readouts compute the paper's own no-visible-attack bound (§1.5.2), O((ln(1/ε)/λ + D)/(1−2α) + D²λ), at ε = 0.01. It grows with λ at fixed D.

The fixed side substitutes Dmax, the D slider. The adaptive side substitutes Dt, the actual-latency slider. That substitution is the whole difference between the two readouts.

Sompolinsky's "about 8x," reproduced twice without inventing a constant. On moving from 10 to 100 blocks a second under GHOSTDAG (Bitcoin Takeover S17 E36, 31:06): "confirmation of transactions will take tens of seconds at least, about 8x long."

At a fixed 2 s delay the bound above gives 43 s at ten blocks a second, his "tens of seconds," and 402 s at 100, a 9.3× increase.

A second, independent check: with D fixed at 5 s, the margin formula verified against bps.rs takes k from 124 blocks at 10 per second to 1,074 at 100, an 8.66× increase. Ten times the blocks buys ten times the speed only if k stays fixed, and GHOSTDAG's own proof forces k up with λ.

KCC-0001 defines the byte layout for a covenant, a rule attached to a coin. The covenant breaker demo attacks a vault covenant with an early withdrawal, a skipped recovery key, and a forged lookalike, and shows the exact rule that stops each one.

What the spec's own authors said about this

This is a simplified stand-in for KCC-0020, a draft token rule that lets an issuer update some holders' cells and not others.

It is not a universal bug. One pattern is defended as intended; a different one its own co-authors call wrong, and the standard does not yet handle it. The table below carries both, with the thread.

“My view is that the combination of extended state, alongside token-specific entry points, allows for various use cases which are not only write-once, nor only for a singleton token. The standard transfer function, though, is meant to transfer fungible tokens, hence, it assumes that inputs and outputs state (excluding ownership and amount) must be identical (or else could not be treated as fungible)” Sivan Helfer (Manyfestation), KCC-0020 co-author · github.com/kaspanet/kccs/issues/14
“I can relate bcs example extensions that come to mind indeed illustrate this. for instance a frozen bool indicator which can be used by stable coin issuer for black listing, indeed renders the token as temporarily non fungible.” Michael Sutton, KCC-0020 co-author · github.com/kaspanet/kccs/issues/14
“I had one conceptual exception, but I think it means it's a wrong pattern. The example would be some contract using the ext state for storing receipt-like information… It mutates all the time but isn't part of the state that matters. I guess this pattern only makes sense if it was well defined as part of the std, and not as an opaque virtual state” Michael Sutton, KCC-0020 co-author · github.com/kaspanet/kccs/issues/14
“I agree that kind of pattern should either be defined in the standard or implemented in a non state storage (maybe the payload, as you once suggested).” Sivan Helfer (Manyfestation), KCC-0020 co-author · github.com/kaspanet/kccs/issues/14

The full thread behind each of the five

Supply split

Issue #14, opened 21 August 2026 by Knitser and still open. KCC-0020's transfer consolidation rule requires every input to carry the same extended-state commitment, but its state-update entrypoint can be authorized only by each cell's own holder.

Update some cells and not others and the supply splits into groups that can never consolidate again, permanently.

Co-authors Manyfestation and Michael Sutton defend one version as intended: Sutton's stablecoin-blacklist example, where a frozen flag deliberately "renders the token as temporarily non fungible."

Sutton then flagged a second pattern, extended state holding ephemeral receipt-like data that mutates without affecting fungibility, as "a wrong pattern." Both co-authors agreed it should be defined in the standard or moved out of state entirely.

ShawnPearce added on 23 August 2026 that the other candidate home for that data, the transaction payload, has its own catch: the v1 sighash commits the payload unconditionally, so it is transaction-scoped rather than per-cell. Under borrowed receive, a borrower who signs the transaction controls the payload the owner's cell is recreated with.

Knitser replied the same day that the explanation "clears it up," so neither of his two proposed fixes was right, and asked the spec to say so plainly in four places. Manyfestation opened PR #16, "Clarify KCC20 extended state fungibility semantics," that day. The issue is open and the pull request has not merged.

Partial conformance

Issue #11, opened 26 July 2026 by KaspaCom, is the only production implementer of a KCC token standard stating its own conformance level in writing: its deployed KCC20V2 "should be described as partially aligned, not fully conforming" with KCC-0001, 0002, 0020 and 0021.

KaspaCom closed the issue itself on 22 August 2026, after the KCC-0021 author explained that its metadata layer is deliberately behavior-independent. That answers KaspaCom's question. It does not withdraw the partial-conformance statement.

Forking templates, and metadata

One launchpad's 74 live tokens span four separate template generations with no migration path between them, only opt-in burn and reissue, per a kas-smiths.org post from 0xKnitser on 15 August 2026.

Covenant tokens have no metadata standard on mainnet without KCC-0021, which stays an open, unmerged pull request, so name, ticker and image all live off-chain. The same post cross-checked one launchpad's logos: 5 of 19 were dead within days, 3 more served HTML instead of an image.

Borrowed receive

Shawn, on the kas-smiths.org forum, 10 July 2026: "borrowed receive lets anyone change your UTXO's outpoint, which griefs pre-signed, outpoint bound transactions." Borrowing a token into a UTXO before a pre-signed spend lands invalidates the transaction and forces a rebuild.

A month later he explained why. "The v1 sighash folds the spent input's own outpoint into the signed message unconditionally," and AnyoneCanPay "only zeroes the other inputs' outpoints, never the signed input's own." Authorization has to move to something the covenant checks against its own state. Nothing has merged.

Read the KCC repository, or follow the discussion on kas-smiths.org. A status word here marks where something sits in this process, never that it works; for what is actually running, use the live status page.
