Why UTXO parallelizes, and the honest tradeoff

Shared, mutable state is what the account model is built to handle: two calls into one balance just need to line up in order, which is why broad contracts landed there first. A coin carries no shared slot to line up, which is why UTXO checks can run at once and a block rate like Kaspa's is possible without having to invent account locks.

Why UTXO parallelizes and an account model doesn't

A payment from an account has to read the current balance, subtract, and write the new balance back, in that order, for that one account. A second payment from the same account has to wait for the first to finish, or the two writes race and the balance goes wrong. That order is a property of the model, not a performance bug: any two spends on the same shared number must be ordered somehow.

A UTXO carries no such shared number. Two coins that belong to two people are two pieces of state. Spending one has nothing to say about spending the other, so a network checking many blocks in parallel can accept both without syncing with each other. That is why a ledger built on coins scales better with block rate: the thing that would need locking in an account model, one shared balance, doesn't exist. Kaspa's blockDAG accepts many blocks in parallel and orders them with GHOSTDAG; a payment system built on separate coins is the shape that fits a high block rate without inventing a way to lock each account.

The one case where UTXO can't parallelize is the same coin spent twice. That's a real conflict, not a queue: just one of the two spends is kept, and the other loses outright. Kaspa settles this with a fixed rule: the first spend of a coin to appear in the ordered record wins, and any later clashing spend loses. Every node runs the same rule over the same DAG and lands on the same answer with no voting round.

The honest cost: broad contracts

The account model's shared, mutable, openly readable balance is really the easier shape for any contract. One contract can hold state, and any other contract can call into it, read that state, and change it, all in the same transaction, because there is one address with one storage slot others can point at. That's what makes something like Ethereum's account based virtual machine a good home for composable, broad logic.

UTXO has no matching shared slot. State lives split up across many coins, and a script can inspect only the spend touching it. It cannot call another coin the way one contract calls another. Writing a broad, composable smart contract platform directly on top of that is really harder.

That's the reason Kaspa's own contract story runs through covenants, not a broad account based virtual machine. A covenant is a rule attached to a coin about how it, and what it makes, are allowed to be spent, checked by script level checks on the spend itself. Post-Toccata mainnet Kaspa has covenants, covenant IDs, and ZKZero-knowledge: a proof that a statement is true without revealing the data behind it, so a script can accept a claim about work done elsewhere without seeing that work. proof checks enforced at the script level. There is no account based VM underneath any of it.

Kaspa's push past that stays inside the one spend being checked, not a shared slot other spends can reach into whenever they like. KIP-16 added an opcode that checks a ZK proof inside a spend, so a script can accept a claim about work done elsewhere without replaying it. Argent's Inter-Covenant Communication uses covenant IDs and checks to let one app's actor allow or watch another's, but only inside a single atomic spend both apps get spent and remade in, and it has shipped so far only in unaudited offline demos. vProgs, aimed at the harder case of many users sharing one app's state across many spends, is a plan with zero releases as of this writing. None of it is an account VM. How far that combining reaches today is its own demo, below.

Why this happens, and what Toccata actually shipped

Kaspa: UTXO. A payment, a token balance, or an app's data on Kaspa lives in one owned, one time spendable cell (a UTXO). Two spends can both target that same cell at once, the way you and the rival just did. Only one confirms. The network does not compare which one paid more or arrived "more validly"; it resolves by which one lands first. The other is rejected outright and has to rebuild against what is left, not merge with the winner and not wait in line behind it.

Account model. Ethereum and similar chains track a running balance or contract state instead of coins spent just once. Two writers to the very same account do not need to reject one another the same way: both actions can apply, one after the other, in whatever order the network settles on. Nobody's write is thrown out just for arriving second; it just lands after the first one instead of in place of it. That behavior, order rather than rejection, is the account side half of the same question this page asks.

This is a simple model of outpoint contention and of account style sequencing, not real network timing (mempool spread, block ordering, gas and fee markets).

What blocks the double spend. Nothing stops two clashing spends from being broadcast in the first place: a wallet can sign and send two spends against the same coin, and the network does not check for that at broadcast time. What cannot happen is both landing in the kept state. It is not a single block rule: a block cannot hold two of its own spends of the same coin, rusty-kaspa's consensus turns that block down outright. But Kaspa is a DAG, so the real race is usually between two blocks landing at the same time, not two spends in one block. GHOSTDAG orders every block into one sequence first, then each block's spends are replayed in that order against a running UTXO diff; whichever spend lands earlier in that order wins, the other block stays valid and stays in the DAG, but its clashing spend fails validation against the state it is checked against and never joins the kept set. That after-the-fact order is also why two actions on separate coins cannot be made to depend on each other the way two calls into one shared account can: each spend is checked against a snapshot GHOSTDAG fixes later, not against a promise that the other side will also succeed. Sources: rusty-kaspa's block body double spend check and the mergeset acceptance loop that orders and replays spends by GHOSTDAG before applying them to the UTXO diff.

What Toccata put on mainnet for this. Three of the KIPs Toccata turned on are the live primitives the panel above runs on. KIP-17 gives a script's check opcodes over the spend touching it: it can read that spend's own inputs, outputs, and payload, not some other spend's. KIP-20 adds covenant IDs, a lineage tag tracked by consensus an output can only carry by continuing a covenant or genesis-initializing a fresh one, so one covenant's record can't be forged. KIP-16 adds an opcode that checks a ZK proof inside a spend, useful for taking a claim about work done without replaying it. None of the three lets a script reach out and read a different covenant's live state the way a function call reads another contract's storage on an account chain; that reading stays scoped to the one spend now being checked.

What composition permits, and why the block doesn't matter. Two apps built apart can compose today, but only inside a single spend that remakes both of them at once. Argent's Inter-Covenant Communication works this way: one app's actor allows or watches another's, and it works because both apps' state sits in the readable inputs and outputs of that one spend. It has shipped so far only in unaudited offline demos, per Argent's README; anyone who says an Argent app is running on Kaspa mainnet today is saying something that has not happened. The line that matters is the spend, not the block: sharing a block with other spends does not link them, the same way two spends in different blocks are no less composed than two in the same block would be. KIP-21's partitioned sequencing lanes (Status: Active) scale how much of that throughput a block can carry; they do not change what a single spend can bind together. Sources: argent-lang/argent, KIP-17, KIP-20, KIP-16, KIP-21.

vProgs, and its status. The gap those two don't close: many users writing to one shared app's state at once (an exchange pool, say), where combining apps on L1 today tends toward an exit style, settling when someone leaves rather than the moment they act. vProgs is a roadmap plan aimed at that gap, not a shipped feature: its own repo README opens with "This repository is in early development / prototype phase. APIs and architecture may change significantly," and as of this writing it carries zero releases and zero tags. Its own architect, Kaspa core developer Michael Sutton, frames the design tradeoff as a choice between "losing synchronous composability or losing sovereignty," and describes one target as "standalone, non-composable sovereign vprogs" settling back to L1 through their own way out, which is the tradeoff the panel shows. Sources: kaspanet/vprogs, Michael Sutton's based-apps design notes.
