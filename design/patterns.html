Compression patterns for a rewrite

Six components, each demonstrated live against real copy pulled from status.html and kips.html. Built on the site's existing custom properties in styles.css, not a new visual language. Every demo works offline, at 375px and desktop, in light and dark, and with keyboard only.

1. Answer block 2. Progressive disclosure 3. Scannable table rows 4. Claim chip 5. Evidence footnote 6. Stat display

Pattern 1 of 6

The answer block

Every page opens with its answer in one or two sentences, before any justification. The reasoning and the sources are reachable from that answer, not a prerequisite for reaching it.

Live demo

Answer

KCC-0020 tokens can permanently split into groups that can never consolidate again. Co-authors defend part of that as intended, but conceded a second pattern is a wrong one needing a spec fix, and the reporter's concern is still open.

Why, and what the co-authors actually said

Issue #14 on the kccs repo shows the transfer consolidation rule requires every input to carry the same extended-state commitment, but only each cell's own holder can authorize a commitment update. The issuer cannot authorize it. Update some cells and not others and supply splits permanently. Co-authors Manyfestation and Michael Sutton defend one pattern as intended: Sutton confirmed it "renders the token as temporarily non fungible" using his own stablecoin-blacklist example. But Sutton then flagged a second pattern, ephemeral receipt-like state that mutates without affecting fungibility, as "a wrong pattern," and both agreed it should either be defined in the standard or moved out of state entirely. Knitser, who reported the issue, has not withdrawn his concern, and no spec change has merged.

Source: kaspanet/kccs issue #14, opened August 21, 2026, still open.

Before and after, from kips.html

Before, live on kips.html

"Anyone weighing whether to issue a token against this draft is asking the right question: what breaks later. Three answers exist today. Issue #14... shows that KCC-0020's transfer consolidation rule requires every input to carry the same extended-state commitment, but its state-update entrypoint can only be authorized by each cell's own holder, not the issuer, so there is no way to move every holder's cell to a new commitment at once. Update some cells and not others and the token's supply splits into groups that can never consolidate again, permanently. Co-authors Manyfestation and Michael Sutton defend one pattern behind this as intended, but Sutton flagged a second pattern as a wrong one needing a spec fix... Separately, issue #11... is the only production implementer... And the standard's own template shape is already fragmenting on mainnet... A token issued against KCC-0020 today inherits a permanent supply-split consequence its co-authors partly defend and partly call a wrong pattern still needing a spec fix, an admitted partial-conformance gap in the one production deployment, and a launchpad that has already forked its own template four times."

271 words, one paragraph, answer arrives in the last sentence.

After, same claim compressed

"Issuing a KCC-0020 token today means inheriting three known defects: a permanent supply-split consequence its co-authors partly defend and partly call a wrong pattern still needing a spec fix, one production deployment that admits partial conformance, and a launchpad already on its fourth incompatible template."

43 words. The three supporting cases (the supply-split consequence, the conformance gap, the template fork) move into three collapsed <details> below it, each with its own source link.

For

The top of every page and every major section. The reader should be able to stop reading after the answer block and be correctly informed, even if less thoroughly.

Not for

Open questions with no settled answer. Forcing a one-sentence verdict onto a genuinely unresolved claim is worse than the wall of text; say "unresolved" and show the competing evidence instead.

Accessibility

  • Answer text is a real paragraph, not an image or a truncated snippet, so it is selectable and readable by screen readers without extra steps.
  • Never hide the answer itself inside a collapsed element. Only the justification collapses.

Pattern 2 of 6

Progressive disclosure

A native <details>/<summary> pair, restyled to look deliberate rather than like unstyled browser chrome. This is the workhorse: it is how a 3,000-word page becomes a 600-word page that still contains all 3,000 words, one click down.

Live demo — try it with Tab and Enter/Space, no mouse

How the DAA-triggered emission step works

Emission steps down every 2,629,800 seconds by a factor of 2-1/12, about 5.61% a step, 426 steps deep in the consensus table. The steps are triggered by DAA score, which is exact. The network went from 25.95654359 KAS/sec at DAA 452,313,000 to 24.49971474 at DAA 478,611,000 to 23.12465141 at DAA 504,909,000, where it sits now.

Source: consensus emission table, cross-checked against mainnet DAA score at time of writing.

For

Reasoning, derivations, edge cases, and anything a reader needs to verify a claim but doesn't need to act on it. The workhorse for turning long pages short.

Not for

The thing the reader came for. A collapsible that hides the actual answer, the actual number, or the actual status is worse than a wall of text, because now it costs a click to find out it was worth reading.

Accessibility

  • Native <details>/<summary>, not a div with a click handler: gets keyboard toggling, correct aria-expanded state, and screen reader announcement of open/closed for free.
  • summary keeps a visible focus ring; do not set outline: none without a replacement.
  • Print stylesheet forces [open] on every details so a printed or PDF-exported page shows everything expanded. See the rule at the bottom of this file.
  • Marker replaced with list-style: none plus a generated affordance, not deleted outright, so the element still reads as a toggle to assistive tech and to the eye.

Keyboard check: focus the summary above, press Enter or Space. It opens. Tab past it, the panel's content is next in tab order only when open.

Pattern 3 of 6

Scannable table rows

status.html has a table cell running 129 words: a paragraph hiding in a grid, which defeats the reason a table exists. A long cell becomes a short cell plus an inline expandable detail, so the row still scans.

Before, actual cell from status.html

ComponentStatus
Argent The README calls the main pieces present: compiler, generated Silverscript, portable artifacts, runtime transaction building, multi-actor routing, and closed and open ICC. The gate it sets for itself is an audit. A production path opens once Silverscript completes its audit and is released, and Argent needs further audit and hardening after that. No release, no tag, no crates.io publish. Breaking changes are still expected before any release. (129 words in this cell.)

After, same cell compressed

ComponentStatus
Argent Compiler and runtime exist, gated on a Silverscript audit. No release, no crates.io publish.
What the README claims

Compiler, generated Silverscript, portable artifacts, runtime transaction building, multi-actor routing, and closed and open ICC are all present per the project's own README. Production readiness is gated on Silverscript's audit landing, then further audit and hardening for Argent itself. Breaking changes are still expected before any release.

For

Any cell that would otherwise run more than about 20 words. The visible cell states the verdict; the detail carries the justification the visible cell doesn't need to earn.

Not for

Cells that are already short, or numeric/status cells where the value itself is the whole answer. Do not add a detail toggle with nothing worth expanding into.

Accessibility

  • details nested inside a td is valid HTML and keeps the row's reading order; verify with a screen reader that the summary reads as part of the cell, not a separate landmark.
  • Never collapse the entire cell, only the elaboration; a reader using a screen reader in table-navigation mode should hear the verdict at minimum.

Pattern 4 of 6

The claim chip

The site already labels everything live, testnet/target, roadmap, research, or wrong, in prose, repeatedly. .status-pill already exists in styles.css and does this as a component; the fix is using it everywhere the words currently get typed out, including inline in sentences.

Live demo, using the site's existing .status-pill

GHOSTDAG ordering Live, 10 BPS Live, Argent Roadmap, Silverscript audit Target, a claim once made about instant finality Wrong.

Instead of: "GHOSTDAG ordering is live on mainnet today, the 10 BPS rate is also live, Argent is still on the roadmap and not shipped, the Silverscript audit is targeted but not complete, and the claim that payments settle instantly is wrong."

For

Any status word appearing inline in a sentence: live, target, roadmap, research, wrong. One glance replaces one clause.

Not for

Nuance that doesn't fit one of the five states. Do not stretch the chip's vocabulary to cover "partially live" or "live but degraded"; write the sentence, or add a sixth state deliberately rather than overload an existing one.

Accessibility

  • Color is never the only signal: the dot is decorative, the label text ("Live", "Roadmap") carries the meaning and is always present.
  • Chip text meets contrast against its background in both themes; verify new status colors the same way the existing five were checked.

Pattern 5 of 6

The evidence footnote

A citation that names the source and states plainly what it does and does not establish, without breaking the sentence it supports. Not just a link; a link plus a one-line scope statement.

Live demo

Mainnet REST reports about 27.655 billion KAS in circulating supply.

ⓘ
Source
Mainnet REST supply endpoint, single node, v2.0.1, synced.

Establishes
The figure that one node reported at query time.

Does not establish
Block or header counts from this endpoint; it spreads reads across backend nodes with different pruning states, so those two figures are unreliable from this source specifically.

For

Any figure or claim where the source has a known scope limit: a single node's view, a self-reported metric, a preprint, a roadmap document describing intent rather than shipped state.

Not for

Every citation on the page. Reserve the "does not establish" line for sources that are genuinely easy to over-read; a plain link suffices when the source's scope is obvious from its name.

Accessibility

  • Definition list keeps source/establishes/does-not-establish as labeled pairs a screen reader announces as term and description, not an unlabeled run of text.
  • The icon is aria-hidden; nothing depends on seeing it.

Pattern 6 of 6

Stat display

A number with its unit, its as-of date, and its source, in a form that reads at a glance and cannot lose its date in a later edit, because the date is a required field of the component, not a trailing clause someone can delete.

Live demo

Emission rate 23.12KAS/sec As of DAA 504,909,000 · consensus emission table
Circulating supply 27.655billion KAS As of query time, single node · REST supply endpoint

For

Any number that changes over time: rates, supply, block counts, TPS figures. The as-of date is what keeps the number honest after the page stops being edited.

Not for

Constants that do not move (a hash function's output size, a fixed protocol parameter). Attaching an as-of date to a constant implies it might change and invites doubt where none belongs.

Accessibility

  • Unit is a separate inline element, never baked into the number as an image or as unlabeled superscript, so the value and unit both reach a screen reader as text.
  • Middot separators are aria-hidden decoration; the meta line still reads correctly as plain text with them removed.

Print and export

Everything expanded on print

A gate to include in a shared stylesheet, so a printed or PDF-exported page never ships a reader a collapsed dead end.

@media print {
  details { display: block; }
  details:not([open]) summary ~ * { display: block !important; }
  details summary::-webkit-details-marker,
  details summary::marker { display: none; }
}
