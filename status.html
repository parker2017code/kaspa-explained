Features and upgrades

Feature Status Meaning Source
Proof of work Live Kaspa runs on proof-of-work mining. Work and new coins never depend on a list of validators. rusty-kaspa
UTXO model Live Kaspa tracks spendable outputs, the same model Bitcoin uses. Ethereum tracks balances instead. rusty-kaspa
GHOSTDAG Live GHOSTDAG keeps blocks that lose the race to be first, instead of throwing them out. It then orders every kept block into one history. Kaspa Research, Research Q&A
Crescendo, ten blocks a second Live Roughly 8 to 9 times the throughput and about 30% faster confirmations. It is not instant finality.
Sutton's numbers, and the claim that overshoots them

Michael SuttonA core Kaspa developer who led the Rust rewrite and much of 2026's covenant and scripting work, including Argent and Silverscript. put the throughput gain at roughly 8 to 9 times and the confirmation-time gain around 30%. A flat "10x faster confirmations" claim goes past his own numbers.

Emission schedule Live Steps down about 5.61% every 30 days, 23.12465141 KAS a second in this step. A block counter triggers each step, not the calendar.
The steps, and why the dates drift

Emission steps down every 2,629,800 seconds by a factor of 2-1/12, 426 steps deep in the consensus table.

It ran 25.95654359 KAS a second at DAA 452,313,000, then 24.49971474 at 478,611,000, then 23.12465141 at 504,909,000, where the network sits now. That step fired around 5 August 2026, and the block reward API moved with it from 2.44997148 to 2.31246515 KAS a block. Next is 21.82676446 at 531,207,000, roughly 4 September 2026.

Calendar dates drift because they depend on how fast blocks land. The DAA triggers do not. No month is a cliff.

Claims people repeat

ClaimVerdictEvidence
Kaspa is proof-of-workLive
What the code says

Kaspa is mined, proof-of-work, full stop. Source: rusty-kaspa.

Kaspa is a blockDAG using GHOSTDAGLive
What GHOSTDAG does

GHOSTDAG orders parallel blocks into one history instead of discarding the losers. Source: the GHOSTDAG walkthrough.

Kaspa produces ten blocks a secondLive
Where the rate is set

Ten blocks a second, the Crescendo-era rate. Source: releases.

Kaspa already runs at 100 blocks a secondResearch
Why not

Ten is live. A hundred is an unconfirmed roadmap proposal with no release, KIP, or code behind it. It exists only in kaspa.org's roadmap prose, which this site stopped citing after that page described Toccata as pre-mainnet eight weeks after activation.

Kaspa payments become irreversible immediatelyWrong
What actually happens

Inclusion is fast. Confidence in a confirmation rises over time rather than switching on. Source: the confirmation-risk demo.

Toccata has activated on mainnetLive
The activation record

Activated at DAA score 474,165,565; v2.0.1 followed as the release. App, wallet, explorer, SDK, and user adoption are separate, still-open checks. Source: the feature table above.

Why not

No. tn10-toc2, tn10-toc3, and the Testnet-10 DAA evidence are testnet-only. v2.0.0 set the mainnet activation score. Source: v2.0.0.

Kaspa has mature native smart contractsNot yet
What is still ahead

Toccata shipped the covenant and proof-check layer only. Mature native DeFi and full app infrastructure are still ahead, through later vProgs work. The three rungs on the UTXO page separate what Toccata put live from what vProgs would add.

July 2026 was a sudden emission cliffMisleading
What the schedule does

Emission steps down by a fixed factor every 2,629,800 seconds, and the DAA score triggers the step rather than the calendar. It went 24.49971474 KAS a second from DAA 478,611,000, then 23.12465141 from 504,909,000, which the network passed around 5 August, then 21.82676446 from 531,207,000, roughly early September. Source: tokenomics.

KCC-0020A Kaspa Call for Conventions: a proposal for how different Kaspa wallets and apps can agree on a shared format, like a token standard. It does not change Kaspa's consensus rules; a KIP does that. is a ratified fungible-token standardNot yet
The defect, and the one production implementer

KCC-0001, KCC-0002, and KCC-0020 merged into the kccs repo, but each still reads Status: Draft in its own body. KCC-0020 also carries a permanent-supply-split consequence, issue #14: its transfer-consolidation rule and its extended-state update entrypoint contradict each other, so a token using the extended-state path can permanently split its own supply.

Co-authors defend one pattern behind this as intended, a frozen or blacklist flag. They conceded a second pattern, ephemeral state that mutates without affecting fungibility, is a wrong one needing a spec fix. The issue remains open with no spec edit.

KaspaCom, the one production implementer on record, calls its own deployed artifact partially aligned rather than fully conforming. Source: kccs repo.

KCC-0021 and KCC-0402 are adopted standards already running in productionWrong
Why not

Both are open, unmerged pull requests. Neither is a merged spec. Their PR bodies claim production use, and those claims live inside the open proposals themselves and could not be independently confirmed. Source: kccs repo.

DAGKnight is current mainnet consensusResearch
Where the branch stands

No. Mainnet ordering runs GHOSTDAG. DAGKnight has a paper and a prototype branch, and the branch is active, with commits as recent as 14 August 2026 promoting its Universal Merge Consensus work. What it does not have is a merge: KIP-2 still reads Status: Proposed. Source: KIP-2 raw file.

vProgs have shipped as production app infrastructureRoadmap
What the repo shows instead

No. Zero releases, zero tags, and the repo calls itself early development. Its tn10-flow example runs against a private testnet-10 fork node, separate from the public one. Source: vprogs repo.

Argent proves Kaspa smart contracts are production-readyResearch
What the README claims is present

No audit yet, and nothing has run on mainnet. Argent's own README says the main pieces are present: compiler, generated Silverscript, portable artifacts, runtime transaction building, multi-actor routing, and closed and open ICC. Silverscript has to finish its own audit first, then Argent needs hardening of its own. Source: Argent README.

Native DeFi has shipped as a mature Kaspa L1 product layerRoadmap
The covenant numbers behind that verdict

Genuine early usage at small scale, with lending still absent from mainnet. Kaskad and Igra-style L2 lending is ecosystem context around Kaspa, separate from native L1 DeFi. See build-on-kaspa for current covenant counts and value; that figure moves fast enough that this page does not restate it.

No feature or claim matches that. Try a broader word like Toccata, DAGKnight, emission, or covenant, or press All.

  • v2.0.0 set the mainnet activation score; v2.0.1 followed.
  • The node setup guide covers upgrades, fee policy, and changed API fields.

 Activation is settled. The open checks after it are wallets, explorers, worked examples, and accepted mainnet transactions.
Toccata KIPs All four read Status: Active in their raw files: KIP-16 (opcodes for verifiable computation), KIP-17 (covenants and scripting), KIP-20 (covenant IDs), KIP-21 (partitioned sequencing commitment). They moved together in one commit on 15 July 2026. The spec repo has caught up with the activation record instead of trailing it.
Open KIP pull requests KIP-24 covers transaction version 1 fields and hashing. KIP-25 covers a compute budget on script execution. KIP-22 proposes a Merkle-root pay-to-script form that hides public keys until spend time. Version 1 transactions and computeBudget already run on mainnet while the KIPs specifying them are open, so cite the operator guide or the node for those two. KIP-22 has no implementation behind it.
Argent argent-lang/argent is an actor-based language and compiler for covenant apps on UTXO rails. It compiles .ag source to Silverscript and portable artifacts that argent-runtime turns into transactions. Two sibling repos appeared in July: argent-playground and argent-template. Compiler and runtime exist. No release, no tag, no crates.io publish, no audit, and nothing on mainnet. The playground demos run offline against fixtures, so none of them is a deployment.
vProgs The kaspanet/vprogs README describes an early-development Rust framework for based computation, with core, storage, state, scheduling, runtime, and node layers. A June merge gathered settlement covenants, batch and aggregation provers, sparse Merkle tree support, and a RISC Zero backend into master. Implementation progress on a roadmap item. Builders can study it now. Production app paths still need their own shipped evidence.
DAGKnight The public dagknight branch is active, most recently promoting Universal Merge Consensus work on 14 August 2026, on top of conflict-zone and lock-removal commits from 13 August. Research and prototype evidence. Mainnet still runs GHOSTDAG, and higher block-rate claims need their own activation record.
Builder tooling kaspa-python-sdk is a standalone public repo. v2.0.0 added Toccata-aligned support and the managed-wallet API for Python; v2.0.1 added get_seq_commit_lane_proof, sync progress events, and covenant-binding fixes. It ships on PyPI. Developer tooling, not protocol status. Upgrade claims still come from node, KIP, and activation evidence.
Indexing PR #860 is open for review. It proposes an optional --txindex, a GetTransaction RPC path, inclusion and acceptance metadata, live updates, and pruning tied to retention-root changes. A separate relay draft explores propagating indexed data. Open, not merged. It would help wallets, explorers, and indexers once it lands.
Running infrastructure? Six paths, and what each has to change

Ordinary wallet users have nothing to do. Everyone below has a row.

Ordinary users

If you hold or send KAS from a normal wallet, there is nothing to do.

Node operators

Run Rusty Kaspa v2.0.1 or newer. The database upgrade only goes one way; the only path back is a resync.

Wallets and submitters

Use fee estimation, or update fixed-fee code to 100 sompi * max(compute grams, 2 * transaction bytes). That floor now binds relayed transactions too, not just direct submissions.

Exchanges and indexers

Update SDKs or regenerate bindings, then handle transaction version 1, storageMass, computeBudget, output covenants, and UTXO covenant_id.

Miners and pools

Test block templates, job distribution, solved block reconstruction, and SubmitBlock against Testnet-10. A block that strips post-Toccata fields can turn invalid after the activation score.

Pool accounting

Check GetBlockRewardInfo, and GetSeqCommitLaneProof where lane-proof data matters. It is the kind of detail that breaks payouts if skipped.

References: Toccata node setup guide and Go Kaspad v0.12.23.
