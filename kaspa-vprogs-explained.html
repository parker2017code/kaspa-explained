Roadmap architecture

vProgs, explained.

Two vProgs transactions touching different resources never wait on each other, no matter how busy the network is. Each transaction declares the state it touches, non-colliding work runs in parallel, and a proof lands on Kaspa L1 instead of a replay of every step.

Status: vProgs are prototype and roadmap work. Toccata is the activated L1 expressiveness surface. Full vProgs and native Kaspa DeFi are not live on mainnet.

One sentence

The mental model

Work that touches the same resource waits in line. Work that doesn't, never sees the line.
Resource

A coin, balance, object, order, vault, game position, or app-specific state item, named so the scheduler can track it.

Dependency

A transaction declares which resources it reads and writes. That declaration is what lets the scheduler decide what can run together.

Proof

The app produces proofs or journals so later layers can verify what happened without re-executing every step on L1.

Scheduling

Why resource lanes exist

A global account model makes every app action compete for the same shared state, even when the actions have nothing to do with each other. vProgs break that state apart into individually addressable resources instead. Alice touching resource A and Bob touching resource Z run at the same time, no queue between them. Two transactions touching the same resource A still have to settle their order, so the scheduler serializes only that piece.

The scheduler builds this from the read/write metadata a transaction declares up front. Each resource behaves like its own lane: a transaction attaches to the lanes it touches, waits only for the values it needs, runs the moment those are ready, then passes its updated state forward. The result is a computational DAG, not a single queue. Independent branches keep executing while a busy resource only slows the transactions that actually collide with it.

Hans Moog's vProgs walkthrough does not claim a raw TPS number. The claim is narrower and more useful: app state that doesn't conflict keeps moving even while one resource or market is under load.

Layer map

What the prototype repo shows

The public kaspanet/vprogs repository calls itself an early-development Rust framework for based computation on Kaspa. Its README splits the framework into six layers: core types, storage, state, scheduling, transaction runtime, and node integration, plus separate L1 and ZK crates for bridge/types, ABI, transaction prover, batch prover, VM, and a RISC Zero backend.

Toccata connection

What comes before full vProgs

Toccata is the hard-fork track that shipped before any of this: activated, not upcoming. Its release and KIP work delivered covenant-style spending rules, covenant IDs, ZK proof checks, and sequencing commitments, concrete handles for UTXO state constraints, app-state identity, selected computation proofs, and app-local sequencing anchored to Kaspa evidence.

Michael Sutton's Argent repo is early tooling evidence, not a finished product: actor-style state machines that generate Silverscript for multi-contract covenant systems. It's prototype work worth studying. Audit, production, and activation are separate claims that need separate evidence.

None of that makes full vProgs live. Toccata can carry simpler covenant apps, proof-gated flows, sequencing commitments, and standalone based-app foundations. Full app-to-app composition, one action touching several app states that succeeds or fails as a unit, is the later target.

For builders

When you actually need it

The vProgs model fits products with many independent pieces of state, many users hitting the same app, or a proof requirement bigger than a covenant spend can carry: trading state, auctions, games, coordination markets, app-specific ledgers, proof-backed settlement.

Most Kaspa apps do not need it yet. Payments, receipts, vault rules, refund paths, allowance caps, and controlled assets fit inside covenants today. Pick the smallest state model that does the job, and reach for vProgs only when your app actually outgrows it.
