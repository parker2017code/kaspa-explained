Claims reference

Claims need a status label

A claim without a label is how confusion spreads. Put it in one lane first: live mainnet, testnet evidence, targeted upgrade, roadmap, research, unsupported, or out of scope.

How to use it

Start with the claim, then ask what evidence it has

Live

Behavior available on Kaspa mainnet now: Proof of Work, UTXO ownership, GHOSTDAG ordering, Crescendo-era 10 BPS, Toccata's activated covenant layer, wallets, nodes, and explorers.

Out of L1 scope

App and project catalog context stays outside this site's status labels unless the claim is specifically about L1 transaction data, accepted transactions, or miner fees.

Testnet-only

TN10/TN12 activation or covenant proof work, accepted testnet transactions, rejected mutation cases, developer-flow evidence. None of it proves mainnet activation on its own.

Targeted

Near-term work where release artifacts, activation parameters, or implementation evidence exist, but mainnet behavior still needs a current check.

Roadmap

vProgs, full cross-app composition, and richer app architecture that still need shipped software and users.

Research

DAGKnight, 100 BPS research, partition-resilient payments, RTD-derived oracle/attestation flows, TangVM, and coordination-market systems.

Editor rule

One sentence test catches most mistakes

If a sentence adds no actor, action, evidence, status label, constraint, consequence, distinction, or reader judgment, delete it.

Tie public wording back to Status, Claims, and Sources. One status label, stated once, then the point directly.
