Toccata status

Kaspa builder guide

Start with the user action, not the architecture: a payment, a vault rule, an asset rule, a market, a proof. Ask about state once that action is specific.

Default: start with the smallest working path. Mainnet status comes from activation, releases, and working applications, not architecture diagrams.

Need terminal commands first? Open Kaspa Command Line From Zero.

1 / Job Name the action

Send, receive, lock, refund, issue, replay, prove, or settle: one verb, not a paragraph.

2 / Path Pick the smallest path

Payment path, app receipt, covenant rule, based app, proof, or later app program: pick the cheapest one that still does the job.

3 / Evidence Show what landed

Accepted txid, app receipt, state output, replay row, source, or release record: something a stranger can check without asking you.

4 / Boundary Say what is missing

Mainnet activation, wallet support, liquidity, audit, indexer, oracle, or production custody: name the actual gap, not "more work needed."

Build around verifiable evidence

A repeatable Kaspa example does four things in order: names the user action, submits or inspects a transaction, replays the result, and labels the evidence class before anyone builds a bigger claim on top of it.

Good first example Payment or receipt

A user sends tKAS or attaches app data; the page links the accepted txid and states exactly what changed.

Good covenant example Rule that blocks a bad spend

Put the cap, destination, required controller input, refund, or timeout in front of the reader before the artifact details.

Weak example Mechanism without a user need

If the demo names the internal mechanism before the user problem, that's the tell.

Start with state and proofs

Question Use this path Simpler path
Many users touch the same app state at the same time. Start with based apps or vProgs-compatible runtime work. Start with covenants and L1 state outputs instead.
The product splits into independent states. Covenants still work, one per separate state. Shared-state app architecture fits better here.
Each action needs its own proof, privacy check, or custom validity rule. Inline ZK is the fit, but it costs more proof and operations work than the alternatives. Covenants or based apps handle this more cheaply.
The proof depends on another chain, an oracle, a price, or a real-world event. The proof stays inside the app's own state rules, no external anchor needed.
The app needs synchronous composition with other independent apps. That's the future full-vProgs direction, especially once several app states must succeed or fail as one operation. Build the narrow app first. Toccata apps coordinate through L1 proofs and sequencing without full atomic composition.

Match app model to state model

Covenants handle constrained spend rules: vaults, treasury controls, escrow-like flows, unlock conditions, issuance policy, small UTXO state machines. One protected state advances one valid step at a time. That constraint is the entire mechanism.

Based apps carry richer app state anchored to Kaspa ordering: balances, orders, packs, risk rows, task states, market state. Start with deterministic replay over accepted transactions. Add ZK only once proof-verified execution, privacy, or trust-minimized bridge logic becomes the actual product boundary, not before.

Inline ZK covers actions that need their own proof before settlement. Full vProgs are the later app-to-app composition direction, where independent apps read or call one another in one combined outcome.

Say what the example buys the user

Attach a user job to every artifact: a budget that can't be drained at once, an asset that only moves under a controller rule, a game turn that can't get stuck forever, a payout that can be replayed, a group payment that refunds if the condition fails.

Show artifacts in this order: what landed on TN12, what the reader can click or repeat, what the repo replayed from accepted rows, which rule is script-enforced versus replay-derived or wallet policy, and what's still missing before this becomes a real product claim.

Keep the boundary honest past that point. Name the script path if the rule is script-enforced. Say so plainly if it's wallet policy, planner state, replay-derived state, or testnet-only evidence. The claim is strongest when the reader can see both the accepted path and the rejected path side by side.

Run every covenant example through the same template: user need, spend rule, accepted path, rejected path, wallet review field, remaining blocker. Say "budget that cannot drain at once," "step-by-step workflow," or "asset that needs its controller" before naming the mechanism.

For the public application framing, see what TN12 covenant tests are teaching. For the current testnet examples, open the TN12 experiment map.

Map product ideas to a path

Pick the smallest path that matches the product. Most first builds land on a wallet/payment path, a covenant-shaped rule, or a narrow based app, not the full stack.

Open product-path table
Product shape Likely starting path Why
Vault, treasury, inheritance, recovery, escrow Covenants Who can move funds, and how the stateful output evolves, is the whole product. Nothing else needed.
Native asset issuance or transfer policy Covenants Asset-native logic stays close to L1 output rules most of the time.
Trading venue, game economy, shared balance app Based app Many users update the same app record at once, without waiting for one UTXO path to clear first.
Private action, custom validity check, proof-gated workflow Inline ZK The proof rides along with every action, so verification is the product boundary, not a feature.
Composable app network with calls across independent apps Full vProgs later App-to-app synchronous composition is the longer architecture target, not a current option.

Builder tools

SDK and node entry points live at Kaspa.org Build and the official getting-started docs. Toccata releases, KIPs, Silverscript, vProgs, ZK SDK, Python SDK, WASM docs, hosted APIs, indexers, and node infrastructure are tracked in Sources.

Hosted APIs work fine for prototypes and dashboards. Products that sign transactions, track balances, handle custody, or promise uptime need a node, an indexer, a provider-redundancy plan, usually all three.

Before prototyping

  1. Pick network first. Mainnet uses kaspa:. TN12 uses kaspatest:. Reusing test keys for mainnet is how funds get lost.
  2. Use the right node. Testnet covenant work needs a branch or release built for that testnet. Mainnet builders run the released mainnet node, not a testnet fork.
  3. Check sync and UTXO index. An unsynced local node or a missing index returns a balance that looks real and isn't.
  4. Separate UI policy from consensus rules. A mockup, planner state, or wallet warning is not an enforced covenant. The chain doesn't know the UI exists.
  5. Record exact submit details. Log SDK version, node version, network id, endpoint, encoding, tx version, and input budget fields every time, not just when something breaks.

Prove the state change

After submit, fetch accepted state and diff it against what the app claims happened. If they match, say so. If they don't, that's the bug report.

Open verification checklist
Builder habit Consequence Check
Fetch accepted state after submit Local construction proves you built a transaction. It doesn't prove the network accepted it. Record `is_accepted`, accepting block data, output script type, address, and amount.
Pin the submit surface REST, JSON wRPC, Borsh wRPC, SDK versions, and testnet branches can each hand back a different transaction shape for the same request. Log SDK version, node version, network id, endpoint, encoding, tx version, and input budget fields.
Compare with a known working spend Witness order, signature preimage, redeem-script shape, and constructor keys are far easier to debug against a sibling transaction that already worked than in isolation. Diff the failing path against an accepted release, refund, or simple payment path before blaming protocol rules.
Label failed attempts narrowly A tooling failure and a consensus failure look identical from the outside. They need different labels or the next builder repeats your mistake. Keep the artifact, but mark it as bad config, stale tooling, submit mismatch, or confirmed consensus rejection.

Testnet lesson: the verification habit transfers, the prototype's status doesn't. One testnet demo is not a mainnet claim.

Say the stage first

  1. Covenants: the L1 state-output path, live on mainnet, for constrained asset and UTXO-state rules.
  2. Based apps: app-specific state anchored to Kaspa ordering, commitments, proofs, settlement, or exits.
  3. Inline ZK: a specialized proof path for actions whose validity or privacy proof is the product boundary.
  4. External anchors: ZK checks a statement about chosen inputs. Builders still have to define how source-chain roots, prices, events, or attestations become trusted inputs. That part isn't automatic.
  5. Based-zk apps: based apps that add proof-verified execution or bridge logic once deterministic replay stops being enough.
  6. Full vProgs: the future app-to-app atomic composition direction, beyond standalone based-app construction.
  7. Transaction payloads: live L1 transaction data for receipts and app context today. Native smart-contract activation is a separate claim with its own evidence.

State the stage plainly first. Add a caveat only where a reader could otherwise mistake builder work for live mainnet functionality.
